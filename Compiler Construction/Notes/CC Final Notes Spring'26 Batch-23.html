1. Language Pre-Processors

Source slides: Week 1 slides 8-17; Week 3 slides 3-4

Language processing prepares a program to run on a computer. The uploaded slides define language processors as systems that verify language rules and convert source programs into executable or lower-level forms.

Preprocessor

A preprocessor produces input for the compiler. In the slides, its highlighted jobs are macro processing and file inclusion, especially header-file inclusion before compilation.

Compiler construction tools named in the slides include scanner generators, parser generators, syntax-directed translation engines, code-generator generators, data-flow analysis engines, integrated compiler toolkits, JFLAP, regex libraries, Flex/Bison, JFlex, ANTLR, LLVM, and JavaCC.

⚡ Key Exam Points

  • A preprocessor runs before the compiler and can expand macros or include files.
  • A compiler translates the entire source program and produces intermediate/object/target code.
  • An interpreter consumes one instruction at a time and reports errors instruction by instruction.
  • Assemblers, linkers, and loaders are separate language-processing stages after compilation.
  • Hybrid systems compile to intermediate code that can be interpreted.

  • Code generation must assign registers carefully because registers are limited.

3. Lexical Analysis

Source slides: Week 1 slides 22-28; Week 2 slides 3-38; Week 3 slides 3-22

Lexical analysis, also called scanning, is the first compiler phase. It reads input characters, groups them into lexemes, produces a token stream for the parser, interacts with the symbol table, strips whitespace/comments, and reports lexical errors with line information.

TermDefinition from slidesExample
LexemeActual substring in code"int", "x", "10"
PatternRule defining valid lexemes[a-z]+ for identifiers
TokenCategorized lexeme(ID, "x") or (INT, 10)

Input Buffering

Lexemes often require lookahead: identifiers end only when a non-alphanumeric character appears, and operators such as < may be part of <=. The two-buffer scheme uses two disk-block-sized buffers, an EOF marker, lexemeBegin at the start of the current lexeme, and forward to scan ahead.

DFA

A deterministic finite automaton has exactly one action for a state/input combination. The slides stress that this lack of ambiguity makes a DFA easy to implement.

NFA

A nondeterministic finite automaton can have ambiguity, such as multiple transitions on the same symbol. The slides use [a-z]*ing for lowercase words ending in ing.

NFA to DFA: Subset Construction

  1. Start with the set containing the NFA start state; if epsilon moves exist, take the epsilon-closure.
  2. For each DFA state, compute where each input symbol can move from any NFA state inside that set.
  3. The resulting set of NFA states becomes a DFA state.
  4. Repeat until no new subsets appear.
  5. Any DFA state containing an NFA accepting state is accepting.

Lexical Errors and Recovery

The slides list too-long identifiers, too-long numeric constants, ill-formed numeric constants, and illegal characters. Recovery techniques include panic mode until a delimiter, transposing adjacent characters, inserting a missing character, deleting an extra character, or replacing one character with another.

Lexical recovery examples

⚡ Key Exam Points

  • Token = token name plus optional attribute value pointing to the symbol table.
  • Whitespace and comments are usually discarded by lexical analysis.
  • FIRST boundary decisions in lexing often need lookahead.
  • NFAs can be converted to DFAs by subset construction.
  • A lexical analyzer may not catch misspelled keywords if the spelling is still a valid identifier.

4. Syntax Analysis: Top-Down

Source slides: Week 4 slides 2-98; Week 5 slides 2-44; Week 6 slides 2-40

Syntax analysis, or parsing, determines how a token string can be generated by a grammar. The slides define a context-free grammar by terminals, nonterminals, productions, and a start symbol. A parse tree has the start symbol at the root, terminals at leaves, and nonterminals as interior nodes.

Ambiguous grammar

A grammar is ambiguous if one terminal string can have more than one parse tree. The slides use arithmetic expressions such as 9-5+2 and 9+5*2 to motivate associativity and precedence rules.

Left Recursion and Left Factoring

Top-down grammar preparation
Direct left recursion:
A ->; A alpha | beta

After elimination:
A  ->; beta A'
A' ->; alpha A' | epsilon

Example from slides:
E  ->; E + T | T
T  ->; T x F | F
F  ->; id

Eliminated:

E' ->; + T E' | epsilon
T  ->; F T'
T' ->; x F T' | epsilon
F  ->; id

Left factoring is used when multiple alternatives share a prefix. For A -> alpha beta1 | alpha beta2, rewrite as A -> alpha A' and A' -> beta1 | beta2.

Recursive Descent

A recursive descent parser is a top-down parser built from mutually recursive functions, one function per nonterminal. It is suitable for LL(1) grammars where a single lookahead token selects the production.

Recursive descent skeleton
parseE():
  parseT()
  parseEPrime()

parseEPrime():
  if lookahead == '+':
    match('+'); parseT(); parseEPrime()
  else:
    use epsilon

parseF():
  if lookahead == '(':
    match('('); parseE(); match(')')
  else if lookahead in {id, num}:
    match(lookahead)
  else:
    error

LL(1) Parsing Table Construction

  1. Check that the grammar has no left recursion, is unambiguous, and is left factored.
  2. Compute FIRST and FOLLOW for all nonterminals.
  3. For each production A -> alpha, put it in table[A,a] for every a in FIRST(alpha).
  4. If epsilon is in FIRST(alpha), put A -> alpha in table[A,b] for every b in FOLLOW(A).
  5. Parse with stack, input buffer, and table entries.

⚡ Key Exam Points

  • Top-down parsing constructs the parse tree from root to leaves.
  • LL(1) means left-to-right scan, leftmost derivation, one lookahead token.
  • Remove left recursion before predictive parsing.
  • Use FIRST to choose productions; use FOLLOW when a production can derive epsilon.
  • Panic-mode predictive recovery pops nonterminals or discards input until synchronizing tokens.

5. Syntax Analysis: Bottom-Up

Source slides: Week 4 slides 89-96; Week 7 slides 2-58

Bottom-up parsers start with the input tokens and repeatedly reduce right-hand sides of productions to their left-hand sides. This is the reverse of a rightmost derivation.

Handle

A handle is the substring matching a production body that should be reduced next in a bottom-up parse. Correct handle choice is crucial because the parser is reconstructing the rightmost derivation in reverse.

Shift-Reduce Parser Actions

AcceptThe start symbol has been recognized and input is consumed.

LR(k), Items, CLOSURE, and GOTO

In the slides, LR(k) means left-to-right scan, rightmost derivation in reverse, and k lookahead symbols. LR parsers maintain states made of items. An LR(0) item is a production with a dot marking parsing progress.

Conflicts

A shift/reduce conflict occurs when the table offers both shifting the lookahead and reducing a handle. A reduce/reduce conflict occurs when two reductions are possible. The slides recommend using the rightmost derivation to understand the correct handle; grammar design, precedence, associativity, or parser-generator declarations can resolve practical conflicts.

⚡ Key Exam Points

  • Bottom-up parsing constructs the parse tree from leaves to root.
  • LR states are sets of items; the dot records how much of a production has been seen.
  • SLR uses LR(0) item sets but places reductions only on FOLLOW sets.
  • CLR(1) uses lookahead inside each item, making it more precise than SLR.
  • LALR merges CLR states with the same LR(0) core, which can introduce conflicts not present in CLR.

6. Semantic Analysis

Source slides: Week 1 slides 32-33; Week 9 slides 2-73; Semantics worksheet

Semantic analysis checks the meaning and logical consistency of a program after lexical and syntax analysis. The slides list type checking, scope resolution, correct function/method calls, declaration checks, and type coercion/casting as core functions.

Error classMeaningExample
Syntax errorViolates grammar/structureMissing semicolon or malformed if statement

SDD and SDT

Syntax-Directed Definition (SDD)

A context-free grammar enhanced with attributes and semantic rules. It describes what semantic values must be computed.

Syntax-Directed Translation (SDT)

A context-free grammar with semantic actions embedded in production bodies. It describes how and when computations happen.

⚡ Key Exam Points

  • Semantic analysis uses the syntax tree and symbol table.
  • Type checking and declaration-before-use are semantic checks.
  • Synthesized attributes flow bottom-up; inherited attributes flow from parent/left siblings.
  • Every S-attributed definition is also L-attributed, but not every L-attributed definition is S-attributed.
  • Postfix SDTs place actions at the ends of productions and execute during reductions.

A directed acyclic graph is like a syntax tree but shares common subexpressions. Leaves are operands; interior nodes are operators. A new node is created only when no node with the same value/operator and operands already exists.

9. Target / Machine Code Generation

Source slides: Week 1 slide 35; Week 15 slides 18-23; practice question file

Target code generation is the final compiler phase. Its input is optimized intermediate representation and its output is target code, often assembly or machine-readable code. Each optimized-code line may map to one or more assembly instructions.

Register allocation

The process of assigning program variables and temporaries to registers. The slides emphasize that registers are fast but limited, so allocation must minimize memory traffic and swaps.

TAC to assembly pattern
TAC:
t1 = x * 5
y  = t1 + 3
z  = t1 * 2

Assembly-style target code:
mov eax, [x]
imul eax, 5
mov [t1], eax
add eax, 3
mov [y], eax
mov eax, [t1]
imul eax, 2
mov [z], eax
Code generator taskExam meaning
Instruction selectionChoose target instructions for each TAC operation
Register allocationMap many temporaries to few registers
Addressing selectionUse suitable memory/register addressing forms
Instruction schedulingOrder instructions while preserving semantics
Target-specific optimizationUse hardware details after target code exists

⚡ Key Exam Points

  • TAC temporaries are unlimited; real registers are limited.
  • Poor register allocation can destroy earlier optimization benefits.
  • RISC targets usually require explicit load/store instructions.
  • CISC targets may allow more complex memory operands.
  • Target code generation is a 1:N mapping from IR instructions to assembly/machine instructions.

1 Parsing Fundamentals Q1: What is the fundamental difference between top-down and bottom-up parsing in terms of parse tree construction? Show SolutionHide Solution

Top-down parsing starts at the start symbol and constructs the parse tree from root to leaves, usually following a leftmost derivation. Bottom-up parsing starts with the input tokens and reduces handles until the start symbol remains, reconstructing a rightmost derivation in reverse.

2 Parsing Fundamentals Q2: Define handle. In bottom-up parsing, why is identifying the correct handle crucial? Show SolutionHide Solution

A handle is the substring on top of the stack that matches the body of the production that must be reduced next. If the parser reduces the wrong handle, it no longer follows the reverse rightmost derivation and can reach a wrong tree or a conflict.

4 Shift-Reduce Parsing Q4: What is a shift-reduce conflict? Give a small grammar example that causes it. Show SolutionHide Solution

A shift/reduce conflict occurs when the parser can either shift the lookahead or reduce the stack handle.

S ->; a A B e
A ->; A b c | b
B ->; d

At stack $ a b with lookahead b, the parser may reduce b ->; A or shift b.
5 Shift-Reduce Parsing Q5: What is a reduce-reduce conflict? Provide an example. Show SolutionHide Solution

A reduce/reduce conflict occurs when the same stack content can be reduced by more than one production.

S ->; b | a A B e
A ->; b
B ->; d

At stack $ b, both S ->; b and A -> b may be possible in a poorly designed table.
6 LR Parsing Q6: What does LR(k) stand for? Explain the meaning of each component (L, R, k). Show SolutionHide Solution

L means scanning input left to right. R means producing a rightmost derivation in reverse. k is the number of lookahead symbols used to decide shift/reduce actions.

7 LR Parsing Q7: Why is LR(1) more powerful than SLR(1)? Show SolutionHide Solution

SLR(1) uses FOLLOW(A) for every completed item A -> alpha., so it may reduce on lookaheads that are too broad. LR(1) stores a specific lookahead inside each item, so reductions occur only in the contexts where they are valid.

8 LR Parsing Q8: What is the canonical collection of LR(1) items? How does it differ from LR(0) items? Show SolutionHide Solution

The canonical LR(1) collection is the full set of LR(1) item states built by CLOSURE and GOTO. An LR(0) item has only a dotted production; an LR(1) item has a dotted production plus a lookahead terminal, written A -> alpha . beta, a.

9 LALR vs LR Q9: How does an LALR(1) parser differ from an LR(1) parser in terms of parse table size and power? Show SolutionHide Solution

Canonical LR(1) keeps all distinct LR(1) states, so its table is larger and most precise. LALR(1) merges LR(1) states with identical LR(0) cores, giving much smaller tables with slightly less power.

10 LALR vs LR Q10: Can an LALR(1) parser have conflicts where LR(1) does not? If yes, why? Show SolutionHide Solution

Yes. When LALR merges states with the same core, their lookahead sets are unioned. A lookahead that was safe in one CLR state may become attached to an item in another state, creating a shift/reduce or reduce/reduce conflict.

11 Practical Parsing Q11: Why is LALR(1) more commonly used in practice than LR(1) for programming languages? Show SolutionHide Solution

LALR(1) tables are much smaller while handling most programming-language grammars. This makes parser generators practical in memory and table size while retaining most LR(1) parsing power.

12 Practical Parsing Q12: In bottom-up parsing, how are syntax errors detected? Compare with top-down error detection. Show SolutionHide Solution

A bottom-up parser detects an error when the ACTION table has no valid entry for the current state/lookahead. A top-down parser detects an error when the stack nonterminal and lookahead have no predictive-table production, or when a terminal on the stack does not match the input.

13 Viable Prefixes Q13: Define viable prefix. Why is the LR parsing algorithm guaranteed to never shift an invalid symbol onto the stack? Show SolutionHide Solution

A viable prefix is a prefix of a right-sentential form that does not extend beyond the right end of a handle. LR automaton states recognize viable prefixes; if no transition/action exists, the parser reports an error instead of shifting.

14 Viable Prefixes Q14: What is the significance of the LR(0) automaton in constructing SLR(1) tables? Show SolutionHide Solution

The LR(0) automaton supplies the parser states and shift/goto transitions. SLR(1) then adds reductions to those states only under FOLLOW sets of the production heads.

15 Ambiguity and Conflicts Q15: Can an ambiguous grammar be used in LR parsing? If so, how are conflicts resolved? Show SolutionHide Solution

An ambiguous grammar usually creates LR conflicts. Parser generators can sometimes still use it if precedence, associativity, or explicit conflict-resolution declarations select the intended action, but an unambiguous grammar is safer for exams.

16 Ambiguity and Conflicts Q16: Explain how operator precedence and associativity can be used to resolve shift-reduce conflicts in LR parsing. Show SolutionHide Solution

If the lookahead operator has higher precedence than the operator in the handle, shift. If the handle operator has higher precedence, reduce. If precedences are equal, left associativity chooses reduce and right associativity chooses shift.

30 SDD / SDT Answer: S-attributed vs L-attributed; why inherited attributes are hard in LR; advantage of SDD/SDT. Show SolutionHide Solution

S-attributed definitions use only synthesized attributes. L-attributed definitions may use inherited attributes, but only from the parent or left siblings, so they can be evaluated left to right.

Inherited attributes do not naturally fit plain LR reductions because LR computes attributes at reduction time after the right-hand side is recognized. Inherited values may be needed before a child is parsed, so marker nonterminals, stack fields, or grammar rewriting may be required.

SDD/SDT integrates semantic computation with grammar structure, making type checking, tree construction, and intermediate-code generation systematic.

(ii) Role of Temporary Variables

Temporary variables (t1, t2, t3, ...) serve as intermediate result holders that ensure each TAC instruction has at most one operator and at most two source operands. They:

  • Decompose complex expressions — A multi-operator expression like a + b * c is broken into t1 = b * c and t2 = a + t1, preserving precedence.
  • Enable optimization — Common subexpression elimination, copy propagation, and dead code removal all work on temporaries.
  • Simplify code generation — Each temporary maps naturally to a register or memory location during target code generation.
  • Make data flow explicit — Dependencies between computations become visible through def-use chains of temporaries.
