1. Syntax Analysis — Complete Overview

Definition: Syntax Analysis (Parsing) is the second phase of a compiler. It takes the stream of tokens produced by the Lexical Analyzer and determines whether the token string can be generated by the grammar of the source language. It produces a parse tree as output.

Role in the Compiler Pipeline

Key Responsibilities

  • Verify that the token stream conforms to the language grammar.
  • Construct a parse tree (concrete syntax tree) from the tokens.
  • Report and recover from syntax errors.
  • Feed the parse tree to the semantic analysis phase.

Parser Classification Tree

2. Introduction to Syntax Analysis / Parsers

Parsing is the process of determining how a string of terminals can be generated by a grammar. The parser must be capable of constructing the parse tree in principle, or else the translation cannot be guaranteed correct.

Key Concepts

  • Lookahead Symbol: The current terminal being scanned in the input. Initially, it is the first (leftmost) terminal of the input string.
  • Top-Down Parsing: Root → Leaves. Corresponds to leftmost derivation.
  • Bottom-Up Parsing: Leaves → Root. Corresponds to rightmost derivation in reverse.

Time Complexity

For any CFG there is a parser that takes at most O(n³) time. For real programming languages, we design grammars parseable in O(n) time using LR or LL methods.

3. Context-Free Grammars (CFG)

Formal Definition: A Context-Free Grammar is a 4-tuple G = (V, T, P, S) where:
  • V — Finite set of variables (non-terminals)
  • T — Finite set of terminals (tokens)
  • P — Finite set of production rules: A → α, where A ∈ V and α ∈ (V ∪ T)*
  • S — Start symbol (S ∈ V)

Key Terminology

  • Terminal: Lexical elements (tokens) — keywords, operators, identifiers, numbers. Leaf nodes in parse trees.
  • Non-Terminal: Syntactic variables (expr, stmt) — internal nodes in parse trees.
  • Production: A rule A → body. Bodies with the same LHS can be grouped with |.
  • Start Symbol: The non-terminal from which all derivations begin.

Example

G = ({S, A, B}, {a, b}, S, {S → AB, A → a, B → b})

Derivation of “ab”:
  S → AB    (S → AB)
    → aB    (A → a)
    → ab    (B → b)

Expression Grammar (Key Example)

list → list + digit | list - digit | digit
digit → 0 | 1 | 2 | … | 9
A CFG is called “context-free” because the left side of every production is a single non-terminal — replacement can happen regardless of surrounding context.

4. Derivations

Definition: A grammar derives strings by beginning with the start symbol and repeatedly replacing a non-terminal by the body of a production. The terminal strings that can be derived form the language defined by the grammar.

4.1 Leftmost Derivation (LMD)

At each step, the leftmost non-terminal is replaced.

Example: Derive digit + digit × digit

Grammar: list → list + list | list × list | digit

list ⇒ list + list
     ⇒ digit + list
     ⇒ digit + list × list
     ⇒ digit + digit × list
     ⇒ digit + digit × digit ✓

4.2 Rightmost Derivation (RMD)

At each step, the rightmost non-terminal is replaced.

Example: Derive digit + digit × digit

list ⇒ list + list
     ⇒ list + list × list
     ⇒ list + list × digit
     ⇒ list + digit × digit
     ⇒ digit + digit × digit ✓

4.3 Parse Tree Derivation

Parse Tree is a graphical representation for derivation. It follows operator precedence — the deepest sub-tree is traversed first.

Properties of a Parse Tree

  • The root is always the start symbol.
  • Interior nodes are non-terminals.
  • Leaf nodes are terminals (reading left-to-right gives the derived string).

Parse Tree for digit × digit + digit

The parse tree is the same for both LMD and RMD of the same derivation choice — only the order of steps differs.

5. Removing Ambiguity from Grammar

Ambiguous Grammar: A grammar that can produce more than one parse tree for some string. Since multiple parse trees imply multiple meanings, we need unambiguous grammars for compilers.

Example of Ambiguity

Grammar: E → E + E | E × E | id
String: id + id × id

Two different parse trees exist:
  Tree 1: (id + id) × id   — wrong precedence
  Tree 2: id + (id × id)   — correct precedence

Two Parse Trees for 9 - 5 + 2

5.1 Resolving Associativity

By convention, 9+5+2 = (9+5)+2 — the + operator is left-associative.

❌ Before (Ambiguous)

E → E + E | E - E | digit

✅ After (Left-Associative)

E → E + digit | E - digit | digit

Right-Associative operators (like = in C) use right recursion:

right → letter = right | letter
a = b = c  is treated as  a = (b = c)

5.2 Resolving Precedence

* has higher precedence than + — it takes its operands before + does.

❌ Before

E → E + E | E × E | id

✅ After (With Precedence)

E → E + T | T
T → T × F | F
F → id

Step-by-Step

  1. + is left-associative with lower precedence: E → E + T
  2. × is left-associative with higher precedence: T → T × F
  3. E can also be just a term: E → E + T | T
  4. T can also be just a factor: T → T × F | F
  5. Base case: F → id
Rule of Thumb: Create one non-terminal per precedence level. Lower precedence → higher in the grammar (closer to start symbol).

Exercises from PPT

Determine whether these are ambiguous:
1. S → (S) | SS | ε           string: ()()()
2. S → SbS | a                string: ababa
3. S → aB | ab, A → AB | a, B → Abb | b   string: ab

6. Eliminating Left Recursion

Left Recursion: A production where the leftmost symbol of the RHS is the same as the LHS non-terminal. Example: A → Aα. Top-down parsers cannot handle left-recursive grammars — they enter an infinite loop.

Types

  • Direct: A → Aα | β
  • Indirect: A → Bα, B → Aβ

6.1 Eliminating Direct Left Recursion

Rule: If A → Aα₁ | Aα₂ | ... | β₁ | β₂ | ... (where no βi starts with A)

Replace with:
A → β₁A' | β₂A' | ...
A' → α₁A' | α₂A' | ... | ε

Algorithm

  1. Identify left-recursive productions A → Aα.
  2. Identify non-recursive productions A → β (where β does NOT start with A).
  3. Create new non-terminal A'.
  4. Write: A → βA' for each non-recursive alternative.
  5. Write: A' → αA' | ε for each recursive alternative.

Example 1

Before

S → Sa | Sb | c | d

After

S  → cS' | dS'
S' → aS' | bS' | ε

Example 2

Before

A → ABd | Aa | a
B → Be | b

After

A  → aA'
A' → BdA' | aA' | ε
B  → bB'
B' → eB' | ε

Example 3: Expression Grammar (Very Important)

Before

E → E + T | T
T → T × F | F
F → id

After

E  → TE'
E' → +TE' | ε
T  → FT'
T' → ×FT' | ε
F  → id

Example 4

Before

S → (L) | a
L → L, S | S

After

S  → (L) | a
L  → SL'
L' → ,SL' | ε

6.2 Eliminating Indirect Left Recursion

Indirect Left Recursion: A → Br, B → Cd, C → At — starting from A we can derive a string beginning with A through a chain.

Algorithm

  1. Order the non-terminals as A₁, A₂, ..., An.
  2. For i = 1 to n: for j = 1 to i−1: substitute Aj productions into Ai.
  3. Eliminate direct left recursion from Ai.

Example

Given:
  A₁ → A₂A₃
  A₂ → A₃A₁ | b
  A₃ → A₁A₁ | a

Step 1: Substitute A₁ → A₂A₃ into A₃:
  A₃ → A₂A₃A₁ | a

Step 2: Substitute A₂ into A₃:
  A₃ → (A₃A₁ | b)A₃A₁ | a
  A₃ → A₃A₁A₃A₁ | bA₃A₁ | a   ← direct left recursion

Step 3: Eliminate direct left recursion:
  A₃ → bA₃A₁A' | aA'
  A' → A₁A₃A₁A' | ε

Final:
  A₁ → A₂A₃
  A₂ → A₃A₁ | b
  A₃ → bA₃A₁A' | aA'
  A' → A₁A₃A₁A' | ε

Example: Another Indirect Recursion

Given:   A → Ba | Aa | c     B → Bb | Ab | d

Step 1: Eliminate left recursion from A:
  A  → BaA' | cA'
  A' → aA' | ε

Step 2: Substitute A into B → Ab:
  B → Bb | BaA'b | cA'b | d

Step 3: Eliminate left recursion from B:
  B  → cA'bB' | dB'
  B' → bB' | aA'bB' | ε
Forgetting to add ε to the new non-terminal A'. The ε production is essential — it allows the recursion to terminate!

7. Left Factoring

Left Factoring: A grammar transformation applied when two or more productions for the same non-terminal share a common prefix. Needed for predictive (top-down) parsing.
Rule: If A → αβ₁ | αβ₂, replace with:
A → αA'
A' → β₁ | β₂

Example 1: if-then-else

Before

stmt → if expr then stmt else stmt
     | if expr then stmt

After

stmt  → if expr then stmt stmt'
stmt' → else stmt | ε

Example 2

Before

A → aAB | aBc | aAc

After

A  → aA'
A' → AD | Bc
D  → B | c

Example 3

Before

S → cAd
A → ab | a

After

S  → cAd
A  → aA'
A' → b | ε
Left factoring may need to be applied multiple times if common prefixes remain after the first pass.

8. FIRST() and FOLLOW()

Why FIRST()?

If the compiler knows the first terminal derivable from a production, it can compare it to the current input token and decide which production to use.

Why FOLLOW()?

When a non-terminal can derive ε, the parser needs to know what terminal can appear after that non-terminal to decide whether to apply the ε-production.

8.1 Rules for FIRST()

FIRST(α) is the set of terminal symbols that begin strings derived from α. If α ⇒* ε, then ε ∈ FIRST(α).
  1. If X is a terminal: FIRST(X) = {X}
  2. If X → ε: add ε to FIRST(X)
  3. If X → Y₁Y₂Y₃:
    • Add FIRST(Y₁) − {ε} to FIRST(X)
    • If ε ∈ FIRST(Y₁), add FIRST(Y₂) − {ε} to FIRST(X)
    • If ε ∈ FIRST(Y₁) AND ε ∈ FIRST(Y₂), add FIRST(Y₃) − {ε} to FIRST(X)
    • If ε ∈ FIRST(Yi) for all i, add ε to FIRST(X)

8.2 Rules for FOLLOW()

FOLLOW(A) is the set of terminals that can appear immediately to the right of A. If A can be rightmost, $ ∈ FOLLOW(A).
  1. Place $ in FOLLOW(S) for start symbol S.
  2. If A → αBβ: add FIRST(β) − {ε} to FOLLOW(B).
  3. If A → αB, or A → αBβ where ε ∈ FIRST(β): add FOLLOW(A) to FOLLOW(B).
Important Notes:
• ε may appear in FIRST() but NEVER in FOLLOW().
• Eliminate left recursion before computing FIRST/FOLLOW!
• FOLLOW(B) is found by looking where B appears on the RHS of productions.

9. Error Handling in Syntax Analysis

Error Handling in predictive parsing involves recovering from syntax errors so the parser can continue finding additional errors.

1. Panic Mode Recovery

The parser skips input symbols until a synchronizing token appears.

  • Pop non-terminal from stack if no matching production exists.
  • Discard/skip input terminals until a synchronizing token (e.g., from FOLLOW set, or delimiters like ; }) is found.

2. Phrase-Level Recovery

Performs local corrections: insert missing semicolons, replace comma with semicolon, delete extraneous symbols.

In LL(1) parsing tables, blank entries are errors. When encountered, error recovery triggers.

10. Top-Down Parsing

Top-Down Parsing builds the parse tree from the root (start symbol) down to the leaves (terminals). Equivalent to finding a leftmost derivation.

How It Works

  1. Start with root labeled with the start symbol.
  2. At node N with non-terminal A, select a production for A.
  3. Create children for the symbols in the production body.
  4. Find the next leftmost unexpanded non-terminal & repeat.
  5. Match terminal nodes with input tokens left to right.

Comparison

FeatureRecursive DescentLL(1) / Predictive
BacktrackingMay or may notNo backtracking (table-driven)
ImplementationMutually recursive functionsStack + Parsing table
GrammarAll kindsOnly LL(k) grammars
DecisionProcedures per non-terminalLookahead + table lookup
Top-down parsing corresponds to pre-order traversal of the parse tree.

11. Recursive Descent Parser

Recursive Descent Parser is a top-down parser where each non-terminal has a corresponding recursive function. It processes input left-to-right, constructing the parse tree by matching production rules.
  • Simple to implement; suitable for LL(1) grammars.
  • Decisions based on a single lookahead token.
  • May use backtracking if grammar is not LL(1).

Pseudocode (Expression Grammar)

Grammar:
  E → TE'    E' → +TE' | ε
  T → FT'    T' → ×FT' | ε
  F → (E) | id | num

function E():
    T();  E_prime()

function E_prime():
    if lookahead == '+':
        match('+');  T();  E_prime()
    else:
        // ε production

function T():
    F();  T_prime()

function T_prime():
    if lookahead == '×':
        match('×');  F();  T_prime()
    else:
        // ε production

function F():
    if lookahead == '(':
        match('(');  E();  match(')')
    elif lookahead == id or num:
        match(lookahead)
    else: error()

Trace: Parsing “4 + 9”

Input: 4 + 9 $
E() → T() → F() → match(4) ✓
      T'() → lookahead='+', not '×' → ε
      E'() → match('+') ✓
            T() → F() → match(9) ✓
                   T'() → ε
            E'() → lookahead='$' → ε
Result: ✅ Accepted

12. LL(1) Parser (Predictive Parser)

LL(1): L = Left-to-right scan, L = Leftmost derivation, 1 = one lookahead. Table-driven, non-recursive. Uses a stack, input buffer, and parsing table.

Essential Conditions

  1. Grammar must be free from left recursion.
  2. Grammar must be unambiguous.
  3. Grammar must be left factored.

Parsing Table Construction Algorithm

  1. Verify conditions (no left recursion, unambiguous, left factored).
  2. Compute FIRST() and FOLLOW() for all non-terminals.
  3. For each production A → α:
    • For each terminal a ∈ FIRST(α): add A → α to M[A, a]
    • If ε ∈ FIRST(α): for each b ∈ FOLLOW(A), add A → α to M[A, b]
    • If ε ∈ FIRST(α) and $ ∈ FOLLOW(A): add A → α to M[A, $]
  4. Undefined entries are errors.

13. Bottom-Up Parsing

Bottom-Up Parsing starts with input tokens (leaves) and works upward toward the start symbol (root). It repeatedly finds handles (substrings matching RHS of productions) and reduces them. This is the rightmost derivation in reverse.
  • Reduction: Replacing RHS with LHS non-terminal.
  • Handle: A substring whose reduction represents one step in the reverse of a rightmost derivation.
  • Handle Pruning: Repeatedly finding and reducing handles.

14. Shift-Reduce Parsing

Shift-Reduce Parsing uses a stack and input buffer. Two main operations: Shift (push next input token onto stack) and Reduce (replace stack-top matching a production RHS with its LHS).

Four Actions

  1. Shift: Push next input symbol onto stack.
  2. Reduce: Pop RHS from stack, push LHS.
  3. Accept: Start symbol on stack, input exhausted.
  4. Error: No valid action.

Example: Parse id - id × id

Grammar: E → E - E | E × E | id
StackInputAction
$id - id × id $Shift id
$ id- id × id $Reduce E→id
$ E- id × id $Shift -
$ E -id × id $Shift id
$ E - id× id $Reduce E→id
$ E - E× id $Shift ×
$ E - E ×id $Shift id
$ E - E × id$Reduce E→id
$ E - E × E$Reduce E→E×E
$ E - E$Reduce E→E-E
$ E$Accept ✓

Conflicts

1. Shift/Reduce Conflict

Parser cannot decide whether to shift or reduce.

Grammar: S→aABe  A→Abc|b  B→d
Stack: $aAb   Input: cde$
Conflict: Shift 'c' or Reduce b→A?

2. Reduce/Reduce Conflict

Multiple reductions possible; can’t decide which.

Grammar: S→aABe|b  A→Abc|b  B→d
Stack: $ab   Input: bcde$
Conflict: Reduce b→S or b→A?
Resolution: Perform Rightmost Derivation first for the given input, then reverse it to determine the correct shift/reduce sequence.

15. LR(0) Parser

LR(0): L = left-to-right scan, R = rightmost derivation in reverse, 0 = zero lookahead. Uses item sets (states) and a DFA for parsing decisions.

Why LR Parsers?

  • Handle virtually all programming language constructs.
  • Most general non-backtracking shift-reduce method.
  • Detect errors as soon as possible. O(n) time.
  • Can handle left-recursive grammars (unlike LL).

LR(0) Items

LR(0) Item: A production with a dot (•) at some position, indicating parsing progress.
For A → XYZ: A → •XYZ, A → X•YZ, A → XY•Z, A → XYZ•
For A → ε: only A → •

Augmented Grammar

Add S' → S. Acceptance = reducing by S' → S.

CLOSURE & GOTO

CLOSURE(I): If A → α•Bβ is in I and B is non-terminal, add B → •γ for every production B → γ. Repeat until no new items.

GOTO(I, X): For each A → α•Xβ in I, create A → αX•β. Then compute CLOSURE of the result.

Solved Example

Grammar: S → AA, A → aA | b

Augmented:
  S' → S   (0)
  S  → AA  (1)
  A  → aA  (2)
  A  → b   (3)

Item Sets

I₀: S'→•S, S→•AA, A→•aA, A→•b
I₁: S'→S•                        (Accept)
I₂: S→A•A, A→•aA, A→•b

16. SLR(1) Parser

SLR(1) — Simple LR(1): Same item sets as LR(0), but reduces are placed only in FOLLOW(LHS) columns, not all terminal columns.

Steps

  1. Write CFG, check ambiguity.
  2. Add augmented production S'→S.
  3. Create canonical LR(0) items (same as LR(0)).
  4. Draw DFA (same as LR(0)).
  5. Build table: shifts same as LR(0); for reduce item A→α•, place reduce only in columns ∈ FOLLOW(A).

17. CLR(1) — Canonical LR Parser

CLR(1) is the most powerful LR parser. Each item has the form [A → α•β, a] where a is a lookahead. Reduces are placed only in the exact lookahead column.

LR(1) Items = LR(0) Items + Lookahead

Lookahead Rules

Case 1: A → α•BC, a

Lookahead for B’s items = FIRST(C). If C can derive ε, also include a.

Case 2: A → α•B, a

Nothing after B → lookahead propagated: B → •D, a

Case 3: A → a | b (alternatives)

Same production family → same lookahead.

18. LALR(1) — Look-Ahead LR Parser

LALR(1) combines power close to CLR(1) with much smaller tables (same size as SLR). It merges CLR states with the same LR(0) core but different lookaheads.

Construction

  1. Build full CLR(1) item sets.
  2. Merge states with same LR(0) core, taking union of lookaheads.
  3. Update table with merged state numbers.

Solved Example

Grammar: S → AA, A → aA | b

  I₈[A→aA•, a/b] + I₉[A→aA•, $] → I₈₉
