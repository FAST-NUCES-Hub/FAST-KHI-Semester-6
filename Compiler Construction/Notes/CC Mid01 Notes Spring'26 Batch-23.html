Compiler Construction — Mid Exam Notes

Ch#1 Introduction · Ch#3 Lexical Analysis · Dragon Book (Aho, Ullman) · Weeks 1–3

1. Language Processors

Language processing is concerned with preparing a program to be run on a computer. Most programs are written in a relatively high-level language.

Language processors verify a program follows its language rules and convert it into machine-executable form. Some language processors perform more translation than others.

A language processor is any tool that manipulates programs — compilers, interpreters, assemblers, linkers, and preprocessors are all language processors.

2. Pre-processor

A pre-processor produces input to compilers. It may perform:

  • Macro processing: Allow user to define macros — shorthand for longer constructs. E.g., #define MAX 100
  • File inclusion: Include header files into program text. E.g., #include <stdio.h>

3. Compiler

A compiler is a translator program that translates a program written in High-Level Language (HLL) — the source program — and translates it into an equivalent program in Machine-Level Language (MLL) — the target program.

An important part of a compiler is error reporting to the programmer.

Source Program (HLL) → [COMPILER] → Target Program (MLL) + Error Messages

4. Assembler

Programmers found it difficult to write or read programs in machine language. They began to use mnemonics (symbols) for each machine instruction.

Such a mnemonic machine language is now called an assembly language. Programs known as assemblers were written to automate the translation of assembly language into machine language.

  • Input to an assembler = Source program (assembly code)
  • Output = Object program (machine language translation)

5. Linker / Loader

After assembly, the object program must be loaded into memory for execution.

  • Early assemblers could load programs directly but wasted memory by staying resident.
  • Loaders were introduced to: place programs in memory, adjust addresses (relocation), and prepare them for execution efficiently.
  • Linkers combine multiple object files and library routines into a single executable.

6. Compiler vs Interpreter

⚡ Compiler

  • Takes entire program as input
  • It is faster at execution
  • Intermediate object code is generated
  • Requires more memory (due to object code)
  • Program need not be compiled every time
  • Errors displayed after entire program is checked
  • Debugging is comparatively hard
  • Examples: C, C++

🐢 Interpreter

  • Takes single instruction as input
  • It is slower
  • No intermediate code is generated
  • Requires less memory
  • Higher level program converted every time
  • Errors displayed for every instruction
  • Debugging is easy
  • Examples: Python, Ruby

7. Hybrid Compilers

Compilation and interpretation may be combined to implement a programming language.

The compiler may produce intermediate-level code which is then interpreted rather than compiled to machine code.

Example: Java — .java → compiled to bytecode (.class) → interpreted by JVM.

Source → [Compiler] → Intermediate Code → [Interpreter/VM] → Output

8. Compiler Construction Tools

  • Parser generators: Automatically produce syntax analysers from grammatical description of a programming language
  • Scanner generators: Produce lexical analysers from a regular-expression description of the tokens of a language
  • Syntax-directed translation engines: Produce collections of routines for walking a parse tree and generating intermediate code
  • Code-generator generators: Produce a code generator from rules for translating each operation of intermediate language into machine language
  • Data-flow analysis engines: Facilitate gathering information about how values are transmitted from one part of a program to another — key part of code optimization
  • Compiler-construction toolkits: Provide an integrated set of routines for constructing various phases of a compiler

10. Lexical Analysis (Introduction)

The first phase of a compiler is called lexical analysis or scanning.

  • Reads the stream of characters making up the source program
  • Groups characters into meaningful sequences called lexemes
  • Produces tokens in the form (token-name, attribute-value)
  • Passes tokens to the next phase — syntax analysis

Lexical Units / Classes

Lexical ClassDescriptionExamples
IdentifiersVariable/function namesposition, rate
ConstantsNumeric/string literals60, 3.14
KeywordsReserved wordsif, while, int
OperatorsArithmetic/relational+, *, <=
PunctuatorsDelimiters;, (, ), {

Tokenizing: position = initial + rate * 60

LexemeTokenExplanation
position(id, 1)Identifier, symbol-table entry 1
=(=)Assignment operator
initial(id, 2)Identifier, symbol-table entry 2
+(+)Addition operator

Token stream: (id,1) (=) (id,2) (+) (id,3) (*) (60)

Blanks separating the lexemes are discarded by the lexical analyzer.

11. Syntax Analysis (Parsing)

The second phase — the parser uses the token components to create a tree-like intermediate representation (syntax tree) depicting grammatical structure.

  • Each interior node = an operation
  • Each child = an argument of that operation

Syntax Tree for position = initial + rate * 60

           =
          / \
      id(1)   +
             / \
          id(2)   *
                 / \
              id(3)  60
  • The * node makes explicit that we must first multiply rate by 60
  • The + node says add the multiplication result to initial
  • The = root says store the final result in position
  • This ordering is consistent with operator precedence (* before +)

12. Semantic Analysis

Uses the syntax tree + symbol table to check semantic consistency with language definition.

  • Gathers type information and saves it in syntax tree or symbol table
  • Type checking: Compiler checks each operator has matching operands
  • Example: Array index must be integer — using float generates an error

Type Coercions

Some type conversions are permitted (called coercions). For example, if operator * is applied to a float (rate) and an integer (60), the compiler may coerce the integer into a float.

           =
          / \
      id(1)   +
             / \
          id(2)   *
                 / \
              id(3) inttofloat
                      |
                     60

13. Intermediate Code Generation

After syntax and semantic analysis, many compilers generate an explicit low-level or machine-like intermediate representation for an abstract machine.

Two important properties: (1) Easy to produce (2) Easy to translate into target machine code.

Three-Address Code Example

t1 = inttofloat(60)
t2 = id3 * t1
t3 = id2 + t2
id1 = t3

Each instruction has at most one operator on the right side — compiler must generate temporary names (t1, t2, t3).

14. Machine Code Generation

The code generator takes intermediate representation and maps it into the target language.

  • Selects registers or memory locations for each variable
  • Intermediate instructions translated into machine instruction sequences
  • Register allocation is a crucial aspect
LDF  R2, id3        // Load rate into R2
MULF R2, R2, #60.0  // R2 = rate * 60.0
LDF  R1, id2        // Load initial into R1
ADDF R1, R1, R2     // R1 = initial + (rate*60.0)
STF  id1, R1        // Store result in position

16. Role of Lexical Analyser

The lexical analyser is the first phase of the compiler. Its responsibilities:

  • Read input characters from source code
  • Group them into lexemes
  • Produce a sequence of tokens as output
  • Send the token stream to the parser for syntax analysis
  • Interact with the symbol table — when an identifier is found, put its information in the symbol table
  • Strip out comments and whitespace (blank, newline, tab)
  • Generate errors related to lexical analysis
  • Track line numbers to associate errors with source lines
Source Code → [Lexical Analyzer] → Token Stream → [Parser]
↕ Symbol Table

17. Input Buffering

Challenge in Lexeme Recognition

Reading source code efficiently is tricky because lexemes often require lookahead (checking extra characters) to confirm boundaries.

Why Lookahead is Needed:

  • Identifiers: End only when a non-alphanumeric character (space, operator) is encountered
  • Multi-character Operators: Single chars like -, =, < could be part of longer ops (->, ==, <=)
  • Examples: x, iffy, &, &&

Solution: Two-Buffer Scheme (Buffer Pair)

  • Handles large lookaheads safely by dividing input into two buffers, allowing seamless scanning
  • Two buffers (size = disk block, e.g., 4096 bytes) alternate to minimize system calls
  • Special eof marker indicates end of file
  • lexemeBegin: Points to the start of the current lexeme
  • forward: Scans ahead to identify lexeme boundaries
Buffer 0: [ ...source characters... | EOF sentinel ]
Buffer 1: [ ...source characters... | EOF sentinel ]
           ^                          ^
      lexemeBegin              forward (scans ahead)
Two-Buffer Scheme minimises system calls (reads large chunks), enables efficient lookahead and backtracking, and the sentinel eliminates per-character EOF checks.

20. Symbol Table

  • Information is collected incrementally by analysis phases and used by synthesis phases for target code

21. Lexical Errors & Recovery

Types of Errors

  • Compile-Time Errors: Lexical Errors, Syntax Errors, Semantic Errors
  • Run-Time Errors: Occur during execution

Lexical Errors

Hard for lexical analyzer to tell errors without aid of other components.

Example: fi (a == f(x)) — Is fi a misspelling of if or an undeclared function? Since fi is a valid identifier lexeme, this error may be handled by the parser.

Common Lexical Errors:

  • Identifiers that are too long: anidentifierrrrrrrr
  • Exceeding length of numeric constants: int i = 454654564654;
  • Ill-formed numeric constants: 45$36
  • Illegal characters: char x[]="FAST NUCES";$

23. Finite Automata (FA)

A finite automaton (FA) is an abstract machine that can represent certain forms of computation.

  • Consists of states (circles) and edges (labeled arrows) between states
  • Each edge labeled with symbol(s) from alphabet Σ
  • Two types: DFA (Deterministic) and NFA (Non-Deterministic)

Formal Definition: FA = (Q, Σ, δ, q₀, F)

QFinite set of states
ΣInput alphabet (finite set of symbols)
δTransition function
q₀Start state (q₀ ∈ Q)
FSet of accepting/final states (F ⊆ Q)

24. DFA — Deterministic Finite Automaton

A DFA is a special case where every state has exactly one outgoing edge for each input symbol.

  • No ambiguity: For every (state, input symbol) pair, there is exactly one next state
  • No ε-transitions allowed
  • Very easy to implement in software/hardware
DFA Example: Accept strings ending in "ab" over Σ = {a, b}

Double circle = accepting state. q0 = start state. Accepts: ab, aab, bab, ababab, etc.

DFA Example: Accept binary strings divisible by 3

States represent remainder when dividing by 3. q0 (rem=0) is accepting. Accepts: ε, 0, 11, 110, 1001, etc.

25. NFA — Non-Deterministic Finite Automaton

An NFA is a valid FA but has ambiguity — from one state, the same input symbol can lead to multiple states.

  • May have ε-transitions (transitions without consuming input)
  • For same (state, symbol), there can be 0, 1, or more next states
  • Accepts if any path through the NFA leads to an accepting state

DFA Properties

  • Exactly one transition per symbol per state
  • No ε-transitions
  • Deterministic execution
  • Easy to implement
  • May have more states than NFA

NFA Properties

  • Multiple transitions per symbol possible
  • ε-transitions allowed
  • Non-deterministic (multiple paths)
  • Harder to simulate
  • Often fewer states than equivalent DFA
NFA Example: Accept strings ending in "ing" over Σ = {a-z}

NFA for regex [a-z]*ing — q0 has two choices on 'i': stay or move to q1 (non-determinism).

26. RE to NFA — Thompson's Construction

Thompson's Construction converts any regular expression into an equivalent NFA using these rules:

Base Cases

1. Single Character 'a'
2. Epsilon (ε) — Empty string

Inductive Rules

3. Union: R₁ | R₂

           ε → [NFA for R₁] → ε
          /                       \
→  (i)                              (f)
          \                       /
           ε → [NFA for R₂] → ε

New start state (i) branches via ε to both sub-NFAs. Both sub-NFAs' final states connect via ε to new final state (f).

4. Concatenation: R₁R₂

→ [NFA for R₁] → ε → [NFA for R₂] → (f)

The final state of NFA(R₁) merges with the start state of NFA(R₂).

5. Kleene Star: R*

              ε (skip loop)
         ┌─────────────────────┐
         │                     ▼
→  (i) ──ε──→ [NFA for R] ──ε──→ (f)
                   ▲      │
                   └──ε───┘
                  (repeat loop)

ε from i to f (accepts empty), ε from R's end back to R's start (repeat), ε from i to R's start.

Thompson's Construction: RE = (a|b)*abb

Step 1: Build NFA for a and b (base cases)

Step 2: Build NFA for a|b (union)

Step 3: Build NFA for (a|b)* (Kleene star)

Step 4: Concatenate with NFAs for a, b, b

The resulting NFA will have ε-transitions and is non-deterministic, but accepts exactly the strings matching (a|b)*abb.

27. NFA to DFA — Subset Construction

Subset Construction (also called Powerset Construction) converts an NFA to an equivalent DFA.

Key Operations:

OperationDescription
ε-closure(s)Set of all states reachable from state s via ε-transitions only
ε-closure(T)Union of ε-closure(s) for all states s in set T
move(T, a)Set of states reachable from any state in T on input symbol a

Algorithm:

  1. Start with DFA start state = ε-closure(NFA start state)
  2. For each unmarked DFA state T and each input symbol a:
    • U = ε-closure(move(T, a))
    • If U is not already a DFA state, add it
    • Add transition T →(a)→ U
  3. Mark T and repeat until all DFA states are marked
  4. A DFA state is accepting if it contains any NFA accepting state

Example: NFA for (a|b)*abb → DFA

Suppose NFA states 0-10, start=0, accept=10:

DFA StateNFA States (ε-closure)On 'a'On 'b'
A{0,1,2,4,7}BC
B{1,2,3,4,6,7,8}BD
C{1,2,4,5,6,7}BC
D{1,2,4,5,6,7,9}BE
E★{1,2,4,5,6,7,10}BC

State E is accepting (contains NFA state 10).

28. Token Recognition using DFA

Each token type has a pattern described by a regular expression. We convert each RE to a DFA, then combine them into a single DFA that recognizes all token types.

DFA for Relational Operators: <, <=, =, ==, !=, >, >=

*other = any character not forming a longer operator. Retract forward pointer after reading.

32. Maximum Munch (Longest Match) Rule

The lexical analyzer always selects the longest possible prefix of the remaining input that matches any valid token pattern.

Purpose:

  • Resolves ambiguities when multiple tokens share a common prefix
  • Ensures deterministic, language-independent tokenization

Examples

InputLongest MatchShorter Alternative
->-> (single operator)- + >
==== (equality)= + =
>>=>>= (shift-assign)>> + =
a-->ba, --, >, ba, -, ->, b
Some languages (e.g., R, Scala) override maximal munch with priority rules (assignment before comparison). These are handled after the longest match is found, by comparing token types.

33. Two-Input Buffer Scheme (Detail)

Problem:

  • Lexer reads input character by character
  • Naïve getchar() per character causes heavy system call overhead
  • Lookahead may require peeking ahead many characters; backtracking is common with maximal munch

Solution:

  • Two fixed-size buffers (e.g., 4096 bytes each) loaded from input file
  • Each buffer ends with a sentinel character (usually EOF = -1)
  • When forward hits sentinel: if EOF → done, else → load next buffer, reset forward
Buffer 0: [ ... data ... | sentinel ]
Buffer 1: [ ... data ... | sentinel ]

Pointers:
  lexemeBegin → start of current token
  forward     → scans ahead to find token end

Backtracking Support

If no token matches the scanned prefix, the lexer backs up by resetting forward to lexemeBegin + 1 (or to the last accepting state) and retries with a shorter match.

34. Integrating Max Munch with Two-Buffer

Step-by-Step Process:

  1. Set lexemeBegin = forward (start of new token)
  2. Advance forward while current prefix matches some token pattern (DFA simulation)
  3. When no further transition exists, backtrack to last accepting state
  4. Emit the corresponding token
  5. Set lexemeBegin = forward (after accepted token)
  6. Repeat

Trace: Input >>=

Buffer: [ '>', '>', '=', ... ]

1. lexemeBegin = 0, forward = 0
2. forward → 1: ">"   ✓ accept as >
3. forward → 2: ">>"  ✓ accept as >>
4. forward → 3: ">>=" ✓ accept as >>=
5. forward → 4: no transition → backtrack to last accept (>>=)
6. Emit token: >>=
7. lexemeBegin = forward = 3 (after '=')

35. Limitations & Edge Cases

Maximal Munch Pitfalls

  • Fortran DO loop: DO 5 I = 1,25 vs DO 5 I = 1.25 — maximal munch reads 1.25 as a single number, missing the loop structure. Requires context-sensitive lexical disambiguation.
  • C++ templates: vector<vector<int>> — >> tokenized as shift operator. Since C++11, parser must reinterpret nested >> as two closing brackets.

Two-Buffer Limitations

  • Unbounded lookahead: Some tokens (e.g., hex float with p) may need arbitrarily many characters — handled by continuing forward, refilling buffers as needed.
  • Sentinel choice: Must not conflict with legitimate input characters; EOF (-1) is safe.

📝 Practice Questions

Conceptual / Short Answer

  1. What is the difference between a compiler and an interpreter?

    A compiler translates the entire HLL program into MLL at once, producing object code. An interpreter translates and executes one instruction at a time with no intermediate object code. Compilers are faster at execution; interpreters are easier to debug.

  2. What is a hybrid compiler? Give an example.

    A hybrid compiler first compiles source to an intermediate code (bytecode), which is then interpreted by a virtual machine. Example: Java — .java compiled to .class bytecode → interpreted by JVM.

  3. Explain the role of the lexical analyzer.

    The lexical analyzer reads input characters, groups them into lexemes, produces tokens (token-name, attribute-value), strips comments/whitespace, interacts with the symbol table, generates lexical errors, and tracks line numbers.

  4. What is the difference between a token, lexeme, and pattern?

    Token = categorized unit (ID, NUM); Lexeme = actual substring ("count", "42"); Pattern = rule describing valid lexemes for a token ([a-z][a-z0-9]* for identifiers).

  5. Why is input buffering needed? Explain the two-buffer scheme.

    Buffering avoids per-character system calls. Two fixed-size buffers (4096 bytes each) alternate; lexemeBegin marks token start, forward scans ahead. Sentinels eliminate per-character EOF checks. When forward hits sentinel, next buffer is loaded.

  6. What is Maximum Munch rule? Give an example where it creates problems.

    Maximum munch = always select the longest matching prefix as a token. Problem: C++ templates vector<vector<int>> — >> is tokenized as shift operator instead of two closing brackets. Since C++11, parser reinterprets this.

  7. Differentiate DFA and NFA.

    DFA: exactly one transition per (state, symbol), no ε-transitions, deterministic. NFA: multiple transitions possible per (state, symbol), ε-transitions allowed, non-deterministic. Every NFA can be converted to an equivalent DFA (subset construction).

  8. What are the error recovery strategies for lexical errors?

    Panic Mode (skip to delimiter), Transpose (swap adjacent chars), Insert (add missing char), Delete (remove extra char), Replace (substitute wrong char).

Quiz-Style Questions (from slides)

Q1: Ambiguous Operator Tokenization

Language has operators ->, --, -, >, and >>. Given input a-->b, how should the lexer tokenize?

Answer: Using maximal munch: a(id) → --(decrement, longest match of --) → >(greater-than) → b(id). The lexer always picks the longest valid token starting from the current position.

Q2: Context-Dependent Token Recognition

In Fortran: DO 10 I = 1, 10 → DO is keyword. But DO10I = 1 → DO10I is identifier. How can a lexer distinguish?

Answer: In Fortran, whitespace is insignificant. The lexer cannot distinguish without lookahead past the = sign to see if there's a comma (loop) or not (assignment). This requires context-sensitive disambiguation — scanning ahead to the comma.

Q3: Python Operator Maximal Munch

Operators: *, **, *=, **=. Tokenize x**=y:

Answer: Maximal munch picks longest valid operator: x(id) → **=(power-assign, longest match) → y(id). Result: [x] [**=] [y].

📋 Solved Paper Format (CC Mid)

Question 1 — Short Objective Questions 10 marks (5 × 2)

Answer in 2-3 lines each.

Q1(a): What is the purpose of a pre-processor?

Ans: A pre-processor produces input to the compiler. It performs macro processing (shorthand for longer constructs like #define) and file inclusion (inserting header files like #include). It runs before the actual compilation begins.

Q1(b): What is the difference between lexeme and token?

Ans: A lexeme is the actual character sequence (substring) in the source code, e.g., "count". A token is the categorized output produced by the lexical analyzer, e.g., (ID, "count"). One token type can have many different lexemes.

Q1(c): What are ε-transitions in NFA?

Ans: ε-transitions are transitions that allow the NFA to move from one state to another without consuming any input symbol. They provide non-determinism and are used in Thompson's construction to combine sub-NFAs using union, concatenation, and Kleene star operations.

Q1(d): What is the symbol table used for?

Ans: The symbol table is a data structure that stores information about source-program identifiers — including name, type, scope, and memory location. It is accessed by all compiler phases: lexical (creates entries), syntax (adds type info), semantic (type checking), and code generation (memory addresses).

Q1(e): Explain the Maximum Munch rule.

Ans: The Maximum Munch (Longest Match) rule states that the lexical analyzer always selects the longest possible prefix of the remaining input that matches any valid token pattern. For example, given operators > and >=, the input >= is tokenized as one >= operator, not > followed by =.
