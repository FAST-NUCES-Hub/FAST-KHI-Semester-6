📐 Week 7: Software Design

Click each concept to expand. Read the examples — they're what stick in quizzes.

What is Software Design?
Foundation▼

Software design is the process of transforming user requirements (from the SRS document) into a form that can be coded. It produces a design document — a blueprint for the system.

Think of it as: SRS → Design Document → Code

🏛️ Roman Architecture Analogy Good software, like a good building, should have:
• Firmness – No bugs that stop it working
• Commodity – Suitable for its intended purpose
• Delight – Pleasurable to use
🎯 What design produces • Data/Class Design – Data structures and relationships
• Architectural Design – Big picture (MVC, Cloud, etc.)
• Interface Design – How users/systems interact
• Component Design – Detailed procedural logic
FURPS Quality Attributes
Must Know▼

FURPS is a checklist of quality targets for any software design:

F – U – R – P – S Functionality – Does it have the right features?
Usability – Can a person use it easily? (human factors)
Reliability – How often does it fail? (MTTF, recovery ability)
Performance – Speed, response time, resource use, throughput
Supportability – Extensibility, adaptability, serviceability
📱 Real-world Example (Banking App) F: Transfer money, view balance
U: 3-tap transaction flow
R: 99.99% uptime, auto-recovery
P: <2 second load time
S: Easy to update when new regulations come
1. Abstraction (Data & Procedural)
Concept▼

Abstraction = hiding complex details to keep things simple. There are two types:

  • Data Abstraction – A collection of data describing an object, hiding internal implementation. E.g., a door object has attributes (weight, type, swing direction) without exposing how they're stored.
  • Procedural Abstraction – A sequence of instructions with a limited, specific function. E.g., open() — you call it without knowing the exact algorithm inside.
🚗 Car Analogy You use drive() — you press the accelerator. You don't need to know about fuel injection, ignition timing, or engine cycles. That's abstraction.
2. Architecture (Design Concept)
Concept▼

Architecture = the complete structure of a software system — how components are organized, packaged, and interact. It provides conceptual integrity.

  • Structural properties – Defines components (modules, objects) and how they interact
  • Extra-functional properties – Addresses performance, reliability, security
  • Families of related systems – Reuse of architectural building blocks
🏢 Building Analogy Architecture = the floor plan and load-bearing structure of a building. You can decorate differently inside (design), but the walls must stay where the architect put them.
3. Patterns
Concept▼

A pattern = "a proven solution to a recurring problem within a specific context". It conveys the essence of a tried-and-tested design.

Pattern Template includes: Name, Intent, Motivation, Applicability, Structure, Participants, Collaborations, Consequences, Related patterns
♻️ Real Example You need to notify multiple parts of your app when data changes. The Observer pattern is a proven solution — subscribe objects to an event and notify them all automatically. You don't reinvent it each time.
4. Modularity
Concept▼

Modularity = dividing software into separate, named, addressable components (modules) that can be integrated to solve the problem.

It is the single attribute that allows a program to be managed easily.

⚠️ Monolithic vs Modular • Monolithic: One huge file with everything — painful to debug, test, or change
• Modular: auth.js, payment.js, notification.js — each handles one thing
📊 Cost Curve Key Insight Too few modules = high integration cost. Too many = high interface complexity. There's an optimal number of modules that minimizes total cost.
5. Information Hiding
Concept▼

Modules must be designed so that their internal information (algorithm, data structures, implementation details) is NOT accessible to modules that don't need it.

Each module has a controlled interface — only what's necessary is exposed.

🏦 ATM Example You interact with the ATM screen (interface). The PIN validation algorithm, database connection string, and encryption logic are all hidden inside. You have no access to them.
6. Functional Independence: Cohesion & Coupling
⭐ High Priority▼

Functional independence = modules with "single-minded" function and minimal interaction with others.

Cohesion – How focused a single module is on ONE thing. HIGH cohesion = GOOD
Coupling – How much modules depend on each other. LOW coupling = GOOD
🎯 Easy Way to Remember High cohesion: Your PaymentModule only handles payments. Not login. Not emails. One job.
Low coupling: PaymentModule doesn't reach into UserModule's internal variables — it calls a public method.
Law of Demeter A method should only send messages to methods in neighboring classes. Don't reach 3 levels deep: a.getB().getC().doSomething() is high coupling!
7. Refinement (Stepwise)
Concept▼

Refinement = a top-down design approach. Start with a general description and break it into smaller, more detailed steps until you can code it.

☕ Making Tea Example Step 1: Make tea
↳ Step 1.1: Boil water
   ↳ Step 1.1.1: Fill kettle with water
   ↳ Step 1.1.2: Turn on kettle
   ↳ Step 1.1.3: Wait until boiling (3 minutes)
↳ Step 1.2: Add tea bag to cup
↳ Step 1.3: Pour water into cup
Each step is refined until it's codeable.
8. Refactoring
Concept▼

Refactoring = reorganizing code/design without changing its external behavior or function. It improves internal structure.

Removes: redundancy, unused elements, inefficient algorithms, poor data structures.

🧹 Example You have 3 functions that all do the same null check. Refactoring: extract it into one checkNull() function. The app behaves identically, but the code is cleaner.
Key distinction: Refactoring ≠ adding new features. Behavior stays the same. Only the internals change.
Design Classes (5 Types)
Must Know▼

Five types of design classes exist in software architecture:

  • User Interface Classes – What the user sees and interacts with
  • Business Domain Classes – Core business logic and rules
  • Process Classes – Implement business processes (workflows)
  • Persistent Classes – Data that persists in databases (Java: mapped to DB tables)
  • System Classes – Software management/control (e.g., java.lang.System)
🛒 E-Commerce Example UI Class: CheckoutPage
Business Domain: Order, Product
Process: PaymentProcessor
Persistent: CustomerRecord (stored in DB)
System: SessionManager
Well-formed Design Class has:
• Completeness – All expected attributes/methods are there
• Primitiveness – One method = one service (no duplicates)
• High Cohesion – Focused on one kind of thing
• Low Coupling – Minimal collaboration with others

🏗️ Week 8: Software Architecture

Architecture is the skeleton of the system. Learn each pattern with its when-to-use rule.

Architecture vs Design — The Difference
Foundation▼
Architecture = the skeleton and high-level infrastructure (abstract view)
Design = code-level decisions — what each module does, class scope, functions (implementation view)

A Design is an instance of an Architecture, just like an object is an instance of a class.
🎯 The Classic Example from Slides Architecture: Client-Server
Designs from it: A Java EE web app OR a .NET web app — same architecture, different designs.

You CANNOT mix these terms. Architecture ≠ Design.
Architecture in Small vs Large
Concept▼
  • Architecture in the Small – Architecture of an individual program. How a single program is decomposed into components. (This course focuses here.)
  • Architecture in the Large – Architecture of complex enterprise systems that include multiple systems, distributed across different computers/companies.
📱 vs 🌐 Example Small: How your Todo app is split into components (UI, logic, storage)
Large: How Amazon's ecosystem of 1000+ microservices communicate across data centers worldwide
The 4+1 Architectural Views (Kruchten)
⭐ High Priority▼

You can't show everything in one diagram. Kruchten's 4+1 model uses multiple views of the same architecture:

  • Logical View – Functional requirements. Key abstractions as classes. Viewer: End User. Uses: Class Diagram, Sequence Diagram.
  • Process View – Non-functional requirements. How system runs at runtime (interacting processes). Viewer: Integrator. Focus: performance, availability.
  • Development View – Code organization. How system is broken into modules for dev teams. Logical organization of code.
  • Physical/Implementation View – Deployment. Which servers, where software is deployed, data centers. Viewer: System Engineer.
  • +1 Scenarios (Use Cases) – The glue that ties all views together.
🏦 Online Banking System Example Logical: Account, Transaction classes
Process: Login process → Session thread → DB query thread
Development: auth-service/, payment-service/ repos
Physical: Web server (AWS EC2) + DB server (RDS) + Load Balancer
MVC Pattern (Model-View-Controller)
⭐ Most Important▼

MVC separates an application into three components. Widely used in modern web applications.

Model – Data related logic. Communicates with controller. May update view.
View – What the end user sees. HTML/CSS. Communicates with controller.
Controller – Processes requests. Gets data from user. Acts as middleman.
📧 Email App (Gmail-like) Model: Email data, user info, inbox list stored in DB
View: The HTML page you see with email list and read pane
Controller: When you click "Delete", controller receives that, tells Model to delete, View refreshes

Popular frameworks: Django (Python), Laravel (PHP), Rails (Ruby), Spring MVC (Java)

MVC is generally used for single graphical workstation applications.

Layered Architecture (N-Tier)
Pattern▼

Components organized in horizontal layers. Each layer is self-independent — interconnected but not dependent. Best when security is highly concerned.

Presentation Layer – User interfaces (web, desktop, mobile)
Business Logic Layer – Business rules, validations, processes
Data Access Layer – Interacts with database (also called Persistence Layer)
Data Store Layer – The actual database
🛒 E-Commerce Example (Customer Info Request) 1. User types "Show John's orders" → Presentation Layer receives
2. → passes to Business Logic: validates user has permission
3. → Data Access Layer: runs SELECT * FROM orders WHERE user='John'
4. → Data Store: database returns results
5. Results flow back up the chain to be displayed
✅ Advantages Separation of concerns, maintainable, testable, easy to update layers separately, changes in one layer don't affect others (if properly isolated)
Repository / Data-Centric Architecture
Pattern▼

Data is stored in a central shared repository. All components interact only through this repository — not directly with each other.

🔧 IDE / Compiler Example (from slides) In Eclipse IDE, all tools (code editor, debugger, compiler, refactoring tool) share one central repository: the project files and AST (Abstract Syntax Tree).

The editor doesn't talk to the debugger directly. Both read/write to the same repository.
📁 Other Examples • Version control systems (Git) — central repo
• Hospital systems — all departments access central patient record DB
• ERP systems — all modules share one data store
Client-Server Architecture
Pattern▼

One or more clients connected to a central server over a network. The server hosts, delivers, and manages resources for clients.

Client – Takes input, sends requests
Server – Receives and processes requests
Load Balancer – Distributes incoming traffic across multiple servers
🌐 Request Lifecycle (from slides) 1. Client requests data from server
2. Load balancer routes request to appropriate server
3. Server processes the request
4. Server queries the database
5. Database returns data to server
6. Server sends data back to client
7. Repeat
📧 Examples Web servers (browser = client, nginx = server), Mail servers (Outlook = client, Exchange = server)
Pipe and Filter Architecture
Pattern▼

A series of components (filters) connected by pipes. Each filter processes its input and produces an output that flows to the next via a pipe.

🔗 How it works Input → [Filter 1] → pipe → [Filter 2] → pipe → [Filter 3] → Output

Each filter is independent and only knows about its input/output stream.
💻 Unix / Linux Command Line Example cat log.txt | grep "ERROR" | sort | uniq | wc -l

cat (read file) → pipe → grep (filter errors) → pipe → sort → pipe → uniq (unique lines) → pipe → wc -l (count)

Each command is a filter. The pipe | connects them.
🎵 Other Examples • Video processing pipelines (decode → resize → encode)
• ETL data pipelines (Extract → Transform → Load)
• Compiler stages (tokenize → parse → optimize → generate code)
Design Patterns (Creational, Structural, Behavioral)
Must Know▼

Design patterns solve reoccurring code-level problems. Three categories:

🏭 Creational – How objects are created Abstract Factory, Builder, Factory Method, Prototype, Singleton
Example: Singleton ensures only ONE instance of a class (like a Logger)
🔌 Structural – How entities relate Adapter, Bridge, Decorator, Facade, Proxy
Example: Adapter converts one interface to another (like a plug adapter)
💬 Behavioral – How objects communicate Command, Iterator, Mediator, Observer, Interpreter
Example: Observer — YouTube notifies all subscribers when a video is uploaded
Architectural Pattern vs Design Pattern
Distinction▼
Architectural Pattern – High-level, system-wide. Deals with overall structure. (MVC, Layered, Client-Server, Microservices, SOA)

Design Pattern – Mid-level, code-level. Deals with specific module/class interactions. (Singleton, Observer, Factory)

Architectural patterns address: Performance, High availability, Scalability, Security, Maintainability, Testing, Deployment, Technology Stack

📐 Analogy Architectural pattern = City planning (where to put roads, buildings, parks)
Design pattern = Interior design of individual rooms
