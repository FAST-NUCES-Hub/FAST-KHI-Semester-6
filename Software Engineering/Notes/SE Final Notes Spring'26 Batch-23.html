Chapter 1 — Introduction to Software Engineering

What is Software Engineering?

Software engineering is an engineering discipline concerned with all aspects of software production from early stages of system specification through to maintaining the system after it has gone into use.

  • Software: Computer programs and associated documentation. Software products may be developed for a particular customer or may be developed for a general market.
  • Good software attributes: Deliver the required functionality, performance to the user, maintainable, robust, user friendly.
  • Fundamental activities: Software specification, software development, software validation and software evolution.

Why Software Projects Fail?

  • Increasing system complexity & advancements in technology — systems have to be built and delivered more quickly; larger, more complex systems are required.
  • Failure to use software engineering methods — designing without a plan and evolving as per needs leads to software that is more expensive and less reliable.

Software Costs & Key FAQs

  • Software costs often dominate computer system costs. Software costs more to maintain than to develop.
  • For systems with long life, maintenance costs may be several times development costs.
  • Roughly 60% development costs, 40% testing costs. For custom software, evolution costs often exceed development costs.
  • SE vs CS: Computer science focuses on theory and fundamentals; SE is concerned with practicalities of developing and delivering useful software.
  • SE vs System Engineering: System engineering is concerned with all aspects of computer-based systems including hardware, software and process engineering. SE is a part of it.

Case Studies from Slides

1. Personal Insulin Pump: Safety-critical system — collects data from blood sugar sensor, calculates insulin required, sends signals to micro-pump. Low blood sugars → brain malfunctioning, coma, death; high blood sugar → eye and kidney damage.

2. Mentcare: Patient information system for mental health care. Key features: individual care management, patient monitoring, administrative reporting. Concerns: privacy, safety, requirement conflicts (privacy vs availability).

3. Wilderness Weather Station: Data collection system measuring temperature, pressure, sunshine, rainfall, wind speed and direction across remote areas.

4. iLearn: Digital learning environment — a service-oriented system with utility services, application services, and configuration services.

Chapter 2 — Software Processes

Software Process Models

A software process is a structured set of activities required to develop a software system. Process models covered:

  • The Waterfall Model
  • Incremental Development
  • Integration and Configuration (Reuse-oriented)

Practically, most large systems use a process that incorporates elements from all these models.

The Waterfall Model

In principle, a phase must be complete before moving onto the next phase.

Phases:

  1. Requirements analysis and definition
  2. System and software design
  3. Implementation and unit testing
  4. Integration and system testing
  5. Operation and maintenance

Drawback: Intolerance to change in requirements after the process is underway. Only appropriate when requirements are well-defined and changes will be fairly limited. Mostly used for large systems engineering projects where plan-driven nature makes coordination easy.

Figure: The Waterfall Model (from Chapter 2 slides)

Incremental Development

Benefits:

  • Reduced changes' cost — cost of accommodating changing customer requirements is reduced
  • Customer feedback ease — easier to get feedback on development work
  • Rapid delivery & deployment of useful software to the customer

Problems:

  • Process is not visible — managers need regular deliverables to measure progress; documentation often skipped
  • System structure degrades as new increments are added — refactoring needed after each increment

Integration & Configuration (Reuse-Oriented)

Based on software reuse. Systems integrated from existing components or COTS (Commercial-off-the-shelf) systems.

Types of reusable software: Stand-alone applications (COTS), packages to be integrated with frameworks, web services.

Key process stages: Requirements specification → Software discovery & evaluation → Requirements refinement → Application system configuration → Component adaptation & integration.

AdvantagesDisadvantages
Reduced costs & risks — less software from scratchRequirements compromises — may not meet real needs
Faster delivery & deploymentLoss of control over evolution of reused elements

Process Activities

The four basic process activities: specification, development, validation, and evolution.

  • Software Specification: Establishing what services are required & constraints. Includes elicitation, specification, and validation.
  • Software Design & Implementation: Converting specification into executable system.
  • Design activities: Architectural design, database design, interface design, component selection & design.
  • Software Validation: V&V — verification (building the product right) and validation (building the right product). Includes development testing, system testing, acceptance testing.
  • Software Evolution: Software is inherently flexible and can change as requirements change.

Process Improvement & CMM

Software Process Improvement means understanding existing processes and changing them to increase product quality and/or reduce costs and development time.

Two approaches:

  • Process Maturity Approach: Focus on improving process and project management; defined maturity levels. For plan-driven approaches.
  • Agile Approach: Focus on iterative development and reduction of overheads; rapid delivery; responsiveness to changing requirements.

The Process Improvement Cycle: Measure → Analyze → Change → Re-measure

Chapter 3 — Agile Software Development

Agile Development Overview

  • Program specification, design and implementation are inter-leaved.
  • System developed as a series of versions or increments with stakeholders involved in specification and evaluation.
  • Frequent delivery of new versions every 2–3 weeks.
  • Minimize documentation overhead.

Principles of Agile:

PrincipleDescription
Customer involvementCustomers closely involved; provide and prioritize requirements; evaluate iterations.
Incremental deliverySoftware developed in increments with customer specifying requirements for each.
People not processSkills of development team recognized; team develops own ways of working.
Embrace changeExpect system requirements to change; design system to accommodate changes.
Maintain simplicityFocus on simplicity in software and development process; eliminate complexity.

Extreme Programming (XP)

Takes an 'extreme' approach to iterative development. Requirements expressed as user stories.

Key Concepts:

  • User Stories: Simple, informal statements of customer about functionalities needed. Written on task cards.
  • Metaphors: Show how system would work.
  • Spike: Very simple program to explore suitability of a proposed solution (similar to prototype).

Scrum

Scrum is an agile method providing a project management framework with three phases:

  1. Initial phase: Outline planning — establish general objectives and design software architecture.
  2. Sprint cycles: Each cycle develops an increment of the system (2–4 weeks).
  3. Project closure: Wrap up, documentation, lessons learned.

Chapter 4 — Requirements Engineering

Requirements & Types

Requirements: The services a customer requires from a system & the constraints under which it operates.

  • User requirements: Written in natural language, non-technical terms; high-level view for stakeholders/managers.
  • System requirements: Structured document with detailed descriptions of functions, services, and constraints; defines what should be implemented; may be part of contract.

Functional Requirements: Specific functionalities the system must provide (e.g., sign up, login, search).

Non-Functional Requirements: Constraints on system's operation — arise from organizational policies, product requirements, or external sources.

NFR TypeDescriptionExample (Hospital System)
ProductConstraints on runtime behaviorSystem available Mon-Fri, 08:30-17:30; downtime ≤ 5 sec/day
OrganizationalDerive from policies & proceduresUsers authenticate using ID cards
ExternalRequirements from regulatory bodiesRespect patient privacy per ethics code

Requirements Engineering Process

Generic activities: Feasibility → Elicitation & Analysis → Specification → Validation (iterative, interleaved).

Requirements Discovery Techniques:

  • Interviewing: Closed interviews (pre-determined questions) and open interviews (explore requirements).
  • Ethnography: Observing how people actually work; good for understanding existing processes but cannot suggest innovation.
  • Scenarios: Structured form of user story — starting situation, normal flow, what can go wrong, concurrent activities, finished state.

Requirements Validation: Checking requirements define the system as per customer desires. Fixing requirements errors after delivery may cost up to 100 times the cost of fixing implementation errors.

Validation techniques: Requirements review, prototyping, test-case generation/TDD.

Requirements Change Management

Reasons for change:

  1. Business/technical environment changes after installation.
  2. System customers vs. users — different people with different needs and budgets.
  3. Diverse user community with conflicting requirements; final system is a compromise.

Requirements management planning includes: Requirements identification (unique IDs), change management process (assess impact & cost), traceability policies, tool support.

Work Breakdown Structure (WBS)

What is WBS?

"A hierarchical decomposition of the total scope of work to be carried out by the project team to accomplish the project objectives and create the required deliverables."

Why is it needed?

  • For activities identification
  • For correct estimation
  • Identify related activities using PERT
  • Creating schedules
  • Project failure risk minimized

When? After finalizing project scope and before project estimation.

Levels: Level 0 = project title → Level 1 = control accounts (4–7 nodes) → Level 2 = work packages → Level 3 = tasks/activities.

Software Project Estimation — Wideband Delphi

The Wideband Delphi Process

Wideband Delphi is a repeatable estimation process where a team generates estimates through consensus.

Steps:

  1. Choose the team: 3–7 project team members + moderator (not project manager ideally).
  2. Kickoff Meeting: Understand project, brainstorm assumptions, generate WBS, agree on unit of estimation.
  3. Individual Preparation: Each member independently generates estimates for each task + additional assumptions.
  4. Estimation Session: Team consensus through multiple rounds. Moderator plots estimates on a line. Individual estimates not discussed. Goal: achieve maximum convergence.
  5. Assemble Tasks: Project manager compiles final task list, estimates and assumptions.
  6. Review Results: Final review with estimation team.

⚠️ Common Mistakes — Part A

  • Confusing Waterfall with Incremental — Waterfall is sequential, Incremental interleaves activities.
  • Mixing up user requirements (natural language, high-level) with system requirements (structured, detailed).
  • Forgetting that functional requirements depend on non-functional ones (e.g., security → authentication).
  • Confusing CMM levels — Level 1 is Initial (chaos), not "basic".
  • WBS levels: Level 0 = project, Level 1 = control accounts, Level 2 = work packages.

Architectural Design — Fundamentals

What is Architectural Design?

The 1st stage in software design process, concerned with understanding how a software system should be organized and designing the overall structure. It is the critical link between design and requirements engineering.

Architectural abstraction levels:

  • Architecture in the small: Architecture of individual programs — how a program is decomposed into components.
  • Architecture in the large: Architecture of complex enterprise systems that include other systems, programs, distributed over different computers.

Advantages of explicit architecture: Stakeholder communication, system analysis over NFRs, large-scale reuse.

4+1 View Model (Krutchen, 1995)

  • Logical view: Key abstractions as objects/classes — relate requirements to entities.
  • Process view: How system interacts with processes at run-time — useful for availability/performance.
  • Development view: Breakdown of software assigned to teams — useful for managers & developers.
  • Physical view: How hardware & software distributed across processors — useful for system engineers.
  • +1 Conceptual view (Hofmeister): Abstract view for product line architecture reuse.

Architecture & NFR Trade-offs

NFRArchitectural Strategy
PerformanceLocalize critical operations in few components; don't use distributed; use large-grain components; use multiple processors.
SecurityLayered architecture with critical assets in inner layers (multi-tier).
SafetyLocalize safety-critical features in small number of subsystems; separate shutdown system.
AvailabilityInclude redundant components for replacement/update on fault occurrence.
MaintainabilityFine-grained components that can be changed; avoid shared data structures.

Conflict: Performance improves with fewer components; maintainability improves with more. Solution: compromise or use multiple architectural styles for separate parts.

Architectural Patterns

Model-View-Controller (MVC)

Separates presentation and interaction from system data into 3 parts:

  • Model: Manages system data and associated operations.
  • View: Defines and manages how data is presented.
  • Controller: Manages user interaction and passes to View and Model.

When used: Multiple ways to view/interact with data; future requirements unknown.

Advantage: Data changes independently of representation. Disadvantage: Additional code complexity.

Figure: MVC Pattern Organization (from Architecture Design 2 slides)

Layered Architecture

Organizes system into layers with related functionality. Each layer provides services to the layer above. Typically: UI → Auth & Authorization → Business Logic → OS/DB.

  • Rules: Upper layer talks to layer below only; no jumping between layers; lower layers never call upper layers.
  • Advantages: Easy to embed NFRs (security); adjacent layer only affected on update; supports multi-platform.
  • Disadvantages: Performance issue (multiple layers); difficult to code (maintaining layer independence).

Repository Architecture

All data managed in a central repository accessible to all system components. Components don't interact directly — only through the repository. Static structure (doesn't change at runtime).

Advantages: Components independent, changes propagated to all, consistent data management.

Disadvantages: Single point of failure, difficult to distribute across computers.

Client-Server Architecture

Runtime organization of distributed systems. Set of servers offering services + clients accessing them via network.

Advantages: Resource sharing, independent servers, no single point failure, transparent upgradation.

Disadvantages: Each service is single point of failure (DoS attacks), unpredictable performance (network dependent).

Pipe and Filter Architecture

Each processing component (filter) is discrete and carries out one type of data transformation. Data flows (as in pipe) from one component to another.

When used: Data processing applications, compilers (lexical analysis → parsing → semantic analysis → code generation).

Advantages: Easy to understand, supports transformation reuse, sequential or concurrent.

Disadvantages: Data format must be agreed between transformations; increases system overhead.

Application Architectures

Application Types

  • Data processing applications: Process data in batches without user intervention.
  • Transaction processing: Process user requests and update information in database. Transaction = atomic sequence of operations.
  • Event processing systems: Actions depend on interpreting events from environment.
  • Language processing systems: Users' intentions specified in formal language, processed and interpreted by system (e.g., compilers).

Design Concepts

Fundamental Design Concepts

Cohesion and Coupling

  • Cohesion: Relative functional strength of a module. A cohesive module performs a single task — ideally do just one thing. High cohesion = good design.
  • Coupling: Relative interdependence among modules. Depends on interface complexity, entry/reference points, data passing. Low coupling = good design.

Design Model Elements

  • Data elements: Data model → data structures → database architecture.
  • Architectural elements: Application domain, patterns & styles.
  • Interface elements: UI design, external interfaces to other systems, internal interfaces between components.
  • Component elements: Internal details — data structures, algorithmic details, interface for access.
  • Deployment elements: Physical computing environment (distributed or standalone).

Software Testing

Testing Fundamentals

Testing: Showing what a program is doing and detecting anomalies. Part of Software V&V (Verification & Validation).

  • Validation: "Are we building the right product?"
  • Verification: "Are we building the product right?"
  • Black-box testing: Testing without checking inner details.
  • White-box testing: Testing each component separately (internal structure).

Testing goals:

  • Validation testing: Confirms system meets user requirements.
  • Defect testing: Find bugs — a successful defect test makes system perform incorrectly.

Stages of Development Testing

  1. Unit testing: Individual program units/object classes tested in isolation. Defect testing process. Test all operations, attributes, and state changes.
  2. Component testing: Multiple units integrated; test components' compatibility and proper data transfer.
  3. System testing: All components integrated; test component interactions, compatibility, correct data transfer.

Test case strategies:

  • Partition testing (Equivalence partitioning): Identify groups of inputs with common characteristics; choose tests from each group + boundary values.
  • Guideline-based testing: Use guidelines reflecting previous experience of common errors.

Basis Path Testing & Cyclomatic Complexity

Basis Path Testing

A white-box testing technique to design test cases ensuring all possible execution paths tested at least once.

Steps:

  1. Label steps in the code.
  2. Create control flow graph using control flow symbols.
  3. Calculate Cyclomatic Complexity (CC) and select independent paths.
  4. Create test cases for each path.
CC = E - N + 2P
Where: E = number of edges, N = number of nodes, P = number of connected components (usually 1)
CC also = number of decision points + 1 (for single program)

Example: Triangle Classifier (from slides)

GIVEN → Code with 4 decision paths: not a triangle, equilateral, isosceles, scalene

PATHS →

Path 1: 1-2-3-10 (Not a triangle)

Path 2: 1-2-4-5-10 (Equilateral)

Path 3: 1-2-4-6-7-10 (Isosceles)

Path 4: 1-2-4-6-8-9-10 (Scalene)

CC = 4 independent paths

CC = 4 (4 test cases needed)

💡 This means we need at minimum 4 test cases to cover all execution paths through this code.

Example 2: Calculate shipping (from slides)

GIVEN → calculate(int amount) function with nextDay check + 6 amount ranges

PATHS →

P-01: 1,2,3,5,7,9,11,13,14

P-02: 1,3,4,14 (amount ≥ 1000)

P-03: 1,3,5,6,14 (amount ≥ 200)

P-04: 1,3,5,7,8,14 (amount ≥ 100)

P-05: 1,3,5,7,9,10,14 (amount ≥ 50)

P-06: 1,3,5,7,9,11,12,14 (amount ≥ 25)

P-07: 1,3,5,7,9,11,13,14 (amount < 25)

CC = 7 paths → 7 test cases needed

Component, Release & User Testing

Interface Testing

Testing components that enable interaction between different components. Interface errors can't be identified from unit testing.

Interface types: Parameter interfaces, Shared memory interfaces, Procedural interfaces, Message passing interfaces.

Types of interface errors: Interface misuse (wrong parameters), Interface misunderstanding (wrong assumptions), Timing errors (shared memory speed mismatch).

Test-Driven Development (TDD)

Tests written before code. Develop code incrementally with a test for each increment.

Benefits: Code coverage, regression testing, simplified debugging, system documentation (tests as documentation).

Release & User Testing

Release testing: Testing for external use — validation testing (black-box). Includes requirements-based testing and performance/stress testing.

User testing types:

  • Alpha testing: Users work with development team at developer's site.
  • Beta testing: Release made available to users (early adopters) to discover problems.
  • Acceptance testing: Customer tests to decide whether to accept and deploy.

User Interface Design

Golden Rules for UI Design (Theo Mandel)

Principle 1: Allow users to maintain control

  • Define interactive modes allowing free user actions with easy switching.
  • Allow flexible interaction (mouse, keyboard, voice, touch).
  • Allow user interaction to be uninterruptable and undoable.
  • Hide technical internals from casual users.
  • Design for direct interaction with on-screen objects.

Principle 2: Reduce user's memory load

  • Use list boxes/checkboxes rather than text boxes.
  • Establish meaningful defaults with reset option.
  • Define intuitive shortcuts (Ctrl+P for print).
  • Disclose information in progressive fashion.

Principle 3: Make consistent interface

  • Allow users to put tasks in meaningful context (labels, consistent color coding).
  • Maintain consistency across family of applications.
  • Don't redefine user's past experiences (e.g., Ctrl+S = save, not scale).

UI Design Issues

  • System response time: Length (longer = user frustration) and variability (varying = user confusion).
  • Help facilities: Availability for all functionalities, how to access, how presented.
  • Error handling: Messages must be explanatory with remedies; describe problem, provide advice, list consequences.
  • Menu & command labeling: How commands assigned to menu items.
  • Accessibility: Cater needs of physically challenged (e.g., voice inputs).
  • Internationalization: Target global market, follow global design standards, multiple languages.

⚠️ Common Mistakes — Part B

  • Confusing Repository (static, central database) with Client-Server (runtime, distributed).
  • MVC: Controller is the middleman, not the View. Model handles data logic.
  • Cyclomatic Complexity CC = E - N + 2P — don't forget 2P (P usually = 1).
  • Cohesion is about module internal strength (high = good); Coupling is about interdependence (low = good).
  • Alpha testing = developer's site; Beta testing = user's site. Don't mix them up.
  • TDD: Tests come BEFORE code, not after.

Estimation of Software — LOC & FP

Lines of Code (LOC) Estimation

Count every line of source code except blanks and comments.

Advantages: Easy to count. Disadvantages: Language dependent — not a good universal metric.

Expected LOC = (S_opt + 4 × S_likely + S_pess) / 6
S_opt = optimistic LOC, S_likely = most likely LOC, S_pess = pessimistic LOC
Effort = Total LOC / (LOC per person-month)
Result in person-months
Cost = Total LOC × Cost per LOC
Or: Cost = Effort × Cost per person-month

Worked Example 1: 3D Geometric Analysis (from slides)

GIVEN → Optimistic = 4,600 LOC, Most Likely = 6,900 LOC, Pessimistic = 8,600 LOC

FIND → Expected LOC

FORMULA → Expected LOC = (S_opt + 4 × S_likely + S_pess) / 6

STEP 1 → = (4,600 + 4 × 6,900 + 8,600) / 6

STEP 2 → = (4,600 + 27,600 + 8,600) / 6

STEP 3 → = 40,800 / 6

Expected LOC = 6,800

💡 Based on three estimates, the expected size is 6,800 lines of code for the 3D geometric analysis component.

Worked Example 2: Travel Booking System (from slides)

GIVEN →

Login & registration: 1,000 LOC | Search & booking: 3,000 LOC | Payment: 2,000 LOC | User profile: 1,500 LOC | Feedback: 500 LOC

Average LOC = 600 LOC/pm | Average cost = $8,000/month

FIND → Effort and total cost

STEP 1 → Total LOC = 1,000 + 3,000 + 2,000 + 1,500 + 500 = 8,000 LOC

STEP 2 → Cost/LOC = $8,000 / 600 = $13.33

Function Point (FP) Estimation

Not language dependent. Measures functionality from user's point of view.

FP Categories:

  • External Inputs (EI): Data entering the system.
  • External Outputs (EO): Data exiting the system.
  • External Inquiries (EQ): Data retrieval without changing system.
  • Internal Logical Files (ILF): Logically related data within application boundary.
  • External Interface Files (EIF): Logical files from other applications used by our system.
FP = UFP × CAF
UFP = Unadjusted Functional Points (sum of counts × weights)
CAF = Complexity Adjustment Factor = 0.65 + (0.01 × ΣFi)
Fi = value adjustment factor from 14 questions (rated 0–5)

Project Scheduling Fundamentals

Project scheduling involves organizing tasks, defining dependencies, and determining the timeline for project completion.

Techniques:

  • Bar charts (Gantt Charts): Horizontal bar chart showing tasks and their durations.
  • Activity Network Diagrams: Show task dependencies and parallel activities.

Activity Network & Critical Path Method (CPM)

Key Terms:

  • ES (Early Start): Earliest time an activity can start.
  • EF (Early Finish): Earliest time an activity can finish. EF = ES + Duration.
  • LS (Late Start): Latest time an activity can start without delaying project.
  • LF (Late Finish): Latest time an activity can finish without delaying project.
  • Total Slack/Float: LS - ES (or LF - EF). Activities with 0 slack = critical path.
  • Free Slack/Float: Amount of time an activity can be delayed without delaying any successor.
EF = ES + Duration
Forward pass: Calculate ES and EF from start to end
LS = LF - Duration
Backward pass: Calculate LS and LF from end to start
Total Float = LS - ES = LF - EF
Float = 0 → Activity is on the Critical Path

Part A Questions (6–8 Questions)

Q1: Part A Explain the difference between generic software and custom software with examples.
▶ Show Answer
Generic software refers to stand-alone systems designed for the open market that serve a wide range of users, such as Microsoft Excel or Mozilla Firefox. These products are developed based on the developer's assessment of market needs, and the users have no control over the development process. Updates are released when market demands change, and the focus is on timely delivery with scalability built-in. Custom software, on the other hand, is commissioned by a specific customer to meet their particular needs, such as an air traffic control system or a hospital management system. The specification of what the software should do and decisions about changes are made by the customer. Custom software might be costly since requirements are specific, but quality is the utmost priority since users are limited and deadlines are more flexible. A key distinction is that generic software development is controlled by the developer organization, while custom software development is driven by the client's requirements.
Q2: Part A Compare the Waterfall model with Incremental development. When would you use each?
▶ Show Answer
The Waterfall model is a plan-driven approach where phases (requirements, design, implementation, testing, maintenance) are completed sequentially — each phase must finish before the next begins. It is best suited for large systems engineering projects where requirements are well-defined and stable, and where coordination among distributed teams is essential. Its main drawback is intolerance to changing requirements. Incremental development, in contrast, interleaves specification, development, and validation activities. The system is developed in increments, with each increment adding new functionality. Key benefits include reduced cost of accommodating changes, easier customer feedback, and rapid delivery of useful software. However, problems include lack of visible process documentation and degradation of system structure as new increments are added. Use Waterfall when: requirements are stable, the project is large with multiple distributed teams, and regulatory compliance requires extensive documentation. Use Incremental when: requirements are expected to change, rapid delivery is important, and customer feedback during development is valuable.
Q3: Part A What are the five levels of the SEI Capability Maturity Model? Explain each briefly.
▶ Show Answer
The SEI CMM rates the maturity of an organization over a 5-point scale. Level 1 (Initial) is the starting point where work is unmanaged, with no proper documentation or project management plans. The vast majority of organizations are at this level. Level 2 (Managed) means goals are satisfied with defined organizational policies, documented project plans, and proper resource management. Level 3 (Defined) involves process management procedures and strategies being defined and used, with proper teamwork and collaborative learning. Level 4 (Quantitatively Managed) focuses on assessing organizational performance with better project management structures and risk analysis through proactive approaches. Level 5 (Optimizing) involves process improvement strategies being defined and used, with increased adaptation to newer trends and continuous innovation in solutions.
Q4: Part A What is the difference between functional and non-functional requirements? Give examples from a hospital system.
▶ Show Answer
Functional requirements define the specific services and functions the system must provide. For a hospital management system, functional requirements include: patients and doctors can register and sign in, each person is identified by an 8-digit ID, users can search doctor appointments across clinics, and doctors can view patient history and medications. Non-functional requirements are constraints on the system's operation that arise from organizational policies, product requirements, or external sources. For the same hospital system, product requirements include the system being available Mon-Fri 08:30-17:30 with downtime not exceeding 5 seconds per day. An organizational requirement is that users authenticate using ID cards. An external requirement is that the system must respect patient privacy per the ethics code. Requirements are not independent — one requirement can constrain another. For example, the non-functional requirement of security will create a functional requirement for user authentication. This interdependency must be carefully managed during requirements engineering.
Q5: Part A Explain the Scrum framework: key terminology, sprint cycle, and benefits.
▶ Show Answer
Scrum is an agile method providing a project management framework with three main phases: an initial outline planning phase to establish objectives and design architecture, a series of sprint cycles where each develops an increment, and a project closure phase that wraps up with documentation and lessons learned. Key terminology includes: the Development team (self-organizing group, max 7 people), Sprint (development iteration of 2-4 weeks), Product backlog (to-do list with user stories and tasks), Product owner (identifies and prioritizes requirements), Scrum Master (arranges meetings, tracks progress, protects team from external distractions), and Sprint Velocity (estimate of backlog effort coverable in one sprint). The sprint cycle begins with a selection phase where the team selects features from the product backlog. During the sprint, the team is isolated from customers with communications channeled through the Scrum Master. At the sprint's end, work is reviewed and presented to stakeholders. Benefits include: the product is broken into manageable chunks, the whole team has visibility of everything improving communication, customers see on-time delivery of increments, and trust between customers and developers is established creating a positive culture.
Q6: Part A Describe the Wideband Delphi estimation process. Why is it effective?
▶ Show Answer
Wideband Delphi is a repeatable estimation process where a team generates estimates through consensus. It follows six steps: First, the project manager selects an estimation team of 3-7 members plus a moderator who should not have a stake in the outcome. Second, in a kickoff meeting, team members understand the project, brainstorm assumptions, review the WBS, and agree on an estimation unit. Third, each member independently prepares estimates for each task with supporting assumptions. Fourth, during the estimation session, the moderator collects forms, plots estimates on a line, the team resolves disagreements (usually about tasks, not individual estimates), and iterates until convergence. Fifth, the project manager assembles the final task list with estimates and assumptions. Sixth, the team reviews the final results together. It is effective because it leverages collective wisdom rather than individual bias, uses multiple rounds to achieve convergence, documents assumptions explicitly, and produces consensus-based estimates that the whole team believes are accurate.

Part B Questions (10–12 Questions)

Q7: Part B Compare the MVC, Layered, and Repository architectural patterns. When would you use each?
▶ Show Answer
The MVC (Model-View-Controller) pattern separates data (Model), presentation (View), and user interaction (Controller). Use it when there are multiple ways to view and interact with the same data, such as web applications where data might be shown in tables, charts, or forms. Its advantage is that data can change independently of its representation, but it adds code complexity. The Layered architecture organizes functionality into hierarchical layers (typically UI, Auth, Business Logic, Database) where each layer provides services only to the layer above. Use it when building on existing systems, when development is spread across teams responsible for different layers, or when multi-level security is required. Its advantage is that entire layers can be replaced if the interface is maintained, but performance can suffer from multiple levels of interpretation. The Repository architecture manages all data in a central repository accessible to all components, with no direct component interaction. Use it when large volumes of data must be stored long-term or in data-driven systems. Its advantage is component independence and consistent data management, but the repository becomes a single point of failure. In summary: MVC for multiple data representations, Layered for team-based development with security needs, and Repository for data-intensive systems with centralized storage.
Q8: Part B What is Cyclomatic Complexity? Calculate CC for a program with 15 edges, 12 nodes, and 1 connected component.
▶ Show Answer
Cyclomatic Complexity (CC) is a software metric that measures the control complexity of a program. It is based on graph theory and is used in Basis Path Testing to determine the minimum number of test cases needed to test all independent execution paths. The formula is CC = E - N + 2P, where E is the number of edges in the control flow graph, N is the number of nodes, and P is the number of connected components (usually 1 for a single program). For the given values: CC = 15 - 12 + 2(1) = 15 - 12 + 2 = 5. This means the program has 5 independent paths, and at least 5 test cases are needed to achieve complete path coverage. A CC value of 5 suggests moderate complexity — programs with CC above 10 are considered difficult to test and maintain.
Q9: Part B Explain the difference between cohesion and coupling. Why is "high cohesion, low coupling" desirable?
▶ Show Answer
Cohesion is an indication of the relative functional strength of a module — how closely the tasks within a module are related. A highly cohesive module performs a single, well-defined task, requiring little interaction with other components. For example, a "CalculateTax" module that only handles tax computation is highly cohesive. Coupling is an indication of the relative interdependence among modules. It depends on the interface complexity between modules, the entry/reference points, and the data that passes across interfaces. Low coupling means modules interact through simple, well-defined interfaces. "High cohesion, low coupling" is desirable because: modules are easier to develop independently (each does one thing well), task scheduling and team assignment become simpler, error propagation is minimized (changes in one module don't cascade), modules become reusable since they are self-contained, and maintenance is easier because changes are localized. This principle is the foundation of functional independence in software design.
Q10: Part B What are the three Golden Rules of UI design by Theo Mandel? Give examples for each.
▶ Show Answer
Theo Mandel defined three golden rules for UI design. First, "Allow users to maintain control" means providing interactive modes with easy switching (like spell check vs editing in Word), supporting flexible interaction methods (mouse, keyboard, voice), allowing undo/redo operations, supporting customization (macros), hiding technical internals from casual users, and enabling direct manipulation of on-screen objects (drag-and-drop). Second, "Reduce user's memory load" means using list boxes and checkboxes instead of requiring users to remember options, providing meaningful defaults with reset capabilities, defining intuitive shortcuts (Ctrl+P for print), matching visual layouts to real-world processes (bill-paying steps mirror real life), and disclosing information progressively (e-commerce showing product images first, then details on click). Third, "Make consistent interface" means using meaningful context for tasks (window labels, consistent color coding), maintaining consistency across a family of applications (same look in all MS Office apps), and never redefining user expectations from past experience (Ctrl+S must always mean save, not scale). These rules ensure the interface is predictable, efficient, and satisfying for users.
Q11: Part B Compare Unit Testing, Component Testing, and System Testing.
▶ Show Answer
Unit testing tests individual program units or object classes in isolation. It is a defect testing process done during the development phase, focusing on testing the functionality of individual objects or methods. Complete coverage involves testing all operations, checking all attributes, and simulating all events causing state changes. Component testing tests multiple integrated units as composite components. It focuses on testing component compatibility and co-existence, particularly proper data transfer between dependent components. This is done during the testing phase and checks that component interfaces behave according to specifications. System testing integrates some or all components and tests the overall system. It focuses on testing component interactions — checking that components are compatible, interact correctly, and transfer the right data at the right time. This is black-box testing where reusable and off-the-shelf components may be integrated with newly developed ones. System testing is a collective process often involving separate testing teams. The key difference is scope: unit testing is isolated components, component testing is integrated units, and system testing is the complete or near-complete system working together.
Q12: Part B What is Test-Driven Development? Explain its process and benefits.
▶ Show Answer
Test-Driven Development (TDD) is an approach where testing and code development are interleaved — tests are written before code, and passing tests is the critical driver of development. The process works as follows: First, identify a small increment of functionality. Second, write an automated test for this functionality. Third, run the test (it will fail since functionality is not yet implemented). Fourth, implement the functionality and re-run the test. Fifth, once all tests pass, move to the next chunk. Benefits include: complete code coverage (every code segment has at least one test), regression testing capability (check if new code breaks previous functionality), simplified debugging (when a test fails, the newly written code is the obvious suspect), and system documentation (tests themselves describe what code should do). TDD can be used with both plan-driven and agile development approaches and significantly reduces the cost of regression testing through automation.
Q13: Part B Explain the 4+1 View Model of software architecture.
▶ Show Answer
The 4+1 View Model, proposed by Krutchen in 1995, presents four basic views of software architecture linked via use cases. The Logical view shows key abstractions as objects or classes, relating system requirements to entities — useful for understanding what the system does. The Process view shows how the system interacts with processes at run-time, useful for making judgments about non-functional requirements like availability and performance. The Development view shows breakdown of software assigned to development teams, useful for project managers and developers planning work. The Physical view shows how hardware and software components are distributed across processors, useful for system engineers. The "+1" refers to the Conceptual view added by Hofmeister et al. (2000), which provides an abstract view of high-level requirements to identify product line architecture for future reuse — deciding which components could be reused for other applications. Each view serves different stakeholders and addresses different concerns, making it impossible to capture all perspectives in a single diagram.
Q14: Part B What is equivalence partitioning in testing? Explain with an example.
▶ Show Answer
Equivalence partitioning is a test case selection strategy where input data and output results are divided into classes (partitions) where all members of a class are expected to be processed in the same way. Instead of testing every possible input, you choose representative test cases from each partition. For example, if a program accepts 4-10 inputs which are 5-digit integers greater than 10,000, the equivalence partitions would be: for the number of inputs — less than 4 (invalid), 4-10 (valid), more than 10 (invalid); for input values — less than or equal to 10,000 (invalid), 10,001-99,999 (valid 5-digit integers greater than 10,000), greater than 99,999 (invalid). Test cases should be chosen from each partition, with particular attention to boundary values (the edges of partitions) since they are typically where errors occur. For instance, testing with exactly 4 inputs and exactly 10 inputs, and with values 10,000 (boundary), 10,001 (just valid), 99,999 (boundary), and 100,000 (just invalid). This approach ensures thorough testing with a manageable number of test cases.
Q15: Part B What is the Pipe and Filter architecture? Give a real-world example.
▶ Show Answer
The Pipe and Filter architecture organizes data processing so that each processing component (filter) is discrete and carries out one type of data transformation. Data flows from one component to another through pipes, like in a UNIX shell. When transformations are sequential, it becomes a batch sequential model. A real-world example is a compiler, where consecutive filters perform: lexical analysis (breaking source code into tokens), parsing (building a syntax tree), semantic analysis (checking for type errors and meaning), and code generation (producing machine code). Each filter takes input, transforms it, and passes the output to the next filter. Advantages include being easy to understand, supporting transformation reuse, matching business process workflows, and being implementable as either sequential or concurrent systems. Disadvantages include the need for agreed data formats between transformations, increased system overhead from parsing/unparsing, and being unsuitable for interactive systems since input data streams (like mouse clicks) are difficult to process as sequential streams.
Q16: Part B Describe Alpha, Beta, and Acceptance testing. How do they differ?
▶ Show Answer
Alpha testing involves users working closely with the development team at the developer's site to test the software. Users provide information to developers to help build effective interface designs and identify issues early. This is a controlled environment where developers can observe user behavior directly. Beta testing makes a release available to users at their own sites to experiment and discover problems. It is done by early adopters of the system who use it in their real working environment and report issues back to developers. The key difference from alpha is that testing occurs in the user's environment, not the developer's. Acceptance testing is when customers formally test a system to decide whether to accept it from developers and deploy it. It follows a structured process: define acceptance criteria, plan testing, derive tests, run tests, negotiate results, and accept/reject the system. It is rarely the case that all tests pass perfectly — usually developers and customers negotiate for acceptance or revision. The key differences are: alpha is developer-site with close collaboration, beta is user-site with independent exploration, and acceptance is formal customer evaluation for deployment decision. All three are forms of user testing that are essential even after comprehensive system and release testing.

Q19: Part C Explain the difference between Quality Assurance and Quality Control.
▶ Show Answer
Quality Assurance (QA) is a proactive, process-oriented approach that focuses on using quality processes and standard procedures to develop a quality product. It involves verification and validation of the product delivered by the development team, ensuring that the development process itself follows established standards. QA is preventive — it aims to prevent defects by improving the process. Quality Control (QC), on the other hand, is reactive and product-oriented. It focuses on testing the actual products and identifying defects to improve product quality. QC happens after the product or component is developed, checking whether it meets specifications and finding bugs. The key distinction is that QA ensures the right process is followed (process quality leads to product quality), while QC checks the end product for defects. Both are essential parts of quality management — QA prevents defects through good processes, and QC catches any defects that slip through. The QM team should be independent from the development team to ensure unbiased reporting.
Q20: Part C List and explain the 7 principles of risk management.
▶ Show Answer
The seven principles to avoid project failure are: (1) Maintain a global perspective — identify all software risks within the scope of application, considering both technical and business risks. (2) Take a forward-looking view — establish contingency plans (plan B) in case of risk occurrence rather than waiting for risks to materialize. (3) Encourage open communication — if someone states a potential risk, do not discount it; create an environment where risks can be discussed freely. (4) Integrate — risk consideration should be integrated into the software development process rather than treated as a separate activity. (5) Emphasize a continuous process — the team continuously monitors for evolving risks and updates mitigation plans. (6) Develop a shared product vision — when all product owners share the same scope, risk assessment becomes more valuable and everyone stays on the same page. (7) Encourage teamwork — pool the talents, skills, and knowledge of all stakeholders to identify and address risks collectively. These principles ensure that risk management is proactive, comprehensive, and embedded in the development culture.
Q21: Part C What are static software product metrics? List and explain at least five.
▶ Show Answer
Static software product metrics are measurements derived from the source code or documentation without executing the program. Five important metrics are: Fan-in/Fan-out: Fan-in measures how many functions call a given function X (high fan-in = X is tightly coupled, changes to X have extensive knock-on effects). Fan-out measures how many functions X calls (high fan-out = high complexity due to control logic needed). Length of code: Measures program size; larger components are generally more complex and error-prone. This is one of the most reliable metrics for predicting error-proneness. Cyclomatic complexity: Measures control complexity of a program (CC = E - N + 2P). Higher values indicate more complex control flow that is harder to understand and test. Depth of conditional nesting: Measures how deeply if-statements are nested. Deeply nested conditionals are hard to understand and potentially error-prone. Fog index: Measures the average length of words and sentences in documentation. Higher fog index means more difficult-to-understand documentation, which impacts maintainability.
Q22: Part C What is the Critical Path in project scheduling? How do you identify it?
▶ Show Answer
The Critical Path is the longest path through an activity network diagram, representing the minimum time required to complete the project. Activities on the critical path have zero total float (slack), meaning any delay in these activities will directly delay the entire project. To identify the critical path: First, perform a forward pass starting from the beginning, calculating Early Start (ES) and Early Finish (EF = ES + Duration) for each activity. When an activity has multiple predecessors, its ES is the maximum EF of all predecessors. Second, perform a backward pass starting from the end, calculating Late Finish (LF) and Late Start (LS = LF - Duration). When an activity has multiple successors, its LF is the minimum LS of all successors. Third, calculate Total Float for each activity (Float = LS - ES = LF - EF). Activities with Float = 0 are on the critical path. The critical path is important for project management because: it determines the shortest possible project duration, any delay on critical path activities delays the entire project, resources should be prioritized for critical path activities, and float on non-critical activities indicates scheduling flexibility.
Q23: Part C What is the LOC expected size formula? Solve: optimistic=2000, most likely=3500, pessimistic=5000 LOC. Productivity = 500 LOC/pm, cost = $7000/month.
▶ Show Answer
The LOC expected size formula uses a weighted average: Expected LOC = (S_optimistic + 4 × S_most_likely + S_pessimistic) / 6. GIVEN: S_opt = 2,000 LOC, S_likely = 3,500 LOC, S_pess = 5,000 LOC, Productivity = 500 LOC/pm, Cost = $7,000/month STEP 1: Expected LOC = (2,000 + 4 × 3,500 + 5,000) / 6 = (2,000 + 14,000 + 5,000) / 6 = 21,000 / 6 = 3,500 LOC STEP 2: Cost per LOC = $7,000 / 500 = $14 STEP 3: Effort = 3,500 / 500 = 7 person-months STEP 4: Total Cost = 3,500 × $14 = $49,000 ANSWER: Expected LOC = 3,500 | Effort = 7 person-months | Cost = $49,000 This means the project is expected to require 7 person-months of effort at a total cost of $49,000.
Q24: Part C Explain RMMM (Risk Mitigation, Monitoring, and Management) with an example.
▶ Show Answer
RMMM stands for Risk Mitigation, Monitoring, and Management — three strategies applied to each identified risk. Mitigation answers "How can we avoid the risk?" — these are proactive strategies to reduce the probability or impact. For example, if there is a risk of key team members leaving (staff turnover risk), mitigation would include cross-training team members, documenting all processes, implementing pair programming so knowledge is shared, and having competitive compensation packages. Monitoring answers "What factors can we track to determine if the risk is becoming more or less likely?" For the staff turnover example, monitoring indicators would include team morale surveys, market salary comparisons, employee satisfaction scores, and attendance patterns of key personnel. Management answers "What contingency plans do we have if the risk becomes reality?" For staff turnover, management plans would include having a recruitment pipeline ready, maintaining updated documentation so new hires can ramp up quickly, and having contract developers available on short notice. This three-pronged approach ensures risks are addressed proactively (mitigation), tracked continuously (monitoring), and handled effectively if they materialize (management).
Q25: Part C What is the inspection checklist? List all fault classes with example checks.
▶ Show Answer
The inspection checklist is a structured list of common errors used during code inspections to systematically identify defects. It is programming-language dependent since behaviors differ at compile time. Research shows that 60% of program defects can be removed through inspections. The fault classes are: Data faults — check if all variables are initialized, constants named, array bounds correct, delimiters assigned, and buffer overflow possible. Control faults — verify each conditional has correct termination, every loop terminates, compound statements are correctly bracketed, all switch cases are accounted for, and break statements are included. Input/Output faults — ensure all input variables are used, output variables assigned before display, and unexpected inputs cannot cause corruption. Interface faults — confirm correct number of parameters, matching parameter types, and correct parameter order. Storage management faults — verify linked structure modifications have correct link reassignment, dynamic storage is properly allocated, and space is deallocated when no longer needed. Exception management faults — check that all possible error conditions have been accounted for.
