1. Software Design Fundamentals

What is Software Design?

Design is where stakeholder requirements, business needs, and technical considerations all come together in the formulation of a product or system.

Software Design is the process of transforming user requirements into some suitable form, which helps the programmer in software coding and implementation. During the software design phase, the design document is produced, based on the customer requirements as documented in the SRS document. Hence the aim of this phase is to transform the SRS document into the design document.

Design allows you to model the system that is to be built. This model can be assessed for quality and improved before code is generated, tests are conducted, and end users become involved in large numbers. Design is the place where software quality is established.

The Roman Architecture Analogy

The Roman architecture notion about well-designed buildings — good software exhibits:

  • Firmness: A program should not have any bugs that inhibit its function.
  • Commodity: A program should be suitable for the purposes for which it was intended.
  • Delight: The experience of using the program should be a pleasurable one.

Why is Design Important?

Design allows you to model the system or product that is to be built. This model can be assessed for quality and improved before code is generated, tests are conducted, and end users become involved in large numbers.

The Design Model

Translating the requirements model into the design model produces four types of design:

Design TypeDescription
Data/Class DesignObjects and relationships defined in the CRC diagram and the detailed data content depicted by class attributes provide the basis for the data design action.
Architectural DesignDefines the relationship between major structural elements of the software. The "Big Picture" — what and why? Where data gets stored, where servers are arranged? Architecture patterns: MVC, Cloud-based. Tradeoffs: may need more space for non-functional requirements.
Interface DesignDescribes how the software communicates with systems that interoperate with it, and with humans who use it. An interface implies a flow of information (data and/or control) and a specific type of behavior.
Component-Level DesignTransforms structural elements of the software architecture into a procedural description of software components.

Design Process

Software design is an iterative process through which requirements are translated into a "blueprint" for constructing the software. As design iterations occur, subsequent refinement leads to design representations at much lower levels of abstraction.

Software Quality Guidelines & Attributes

Throughout the design process, the quality of the evolving design is assessed with a series of technical reviews. McGlaughlin [McG91] suggests three characteristics that serve as a guide for the evaluation of a good design:

  1. The design must implement all of the explicit requirements contained in the requirements model, and it must accommodate all of the implicit requirements desired by stakeholders.
  2. The design must be a readable, understandable guide for those who generate code and for those who test and subsequently support the software.
  3. The design should provide a complete picture of the software, addressing the data, functional, and behavioral domains from an implementation perspective.

Quality Guidelines

  • A design should exhibit an architecture.
  • A design should be modular.
  • A design should contain distinct representations of data.
  • A design should lead to data structures.
  • A design should lead to interfaces that reduce the complexity of connections.

FURPS Quality Attributes

The FURPS quality attributes represent a target for all software design:

AttributeDescription
F — FunctionalityAssessed by evaluating the feature set and capabilities of the program.
U — UsabilityAssessed by considering human factors. Usability is how easily a person can accomplish a given task with your product.
R — ReliabilityEvaluated by measuring the frequency and severity of failure, accuracy of output results, the mean-time-to-failure (MTTF), the ability to recover from failure, and the predictability of the program.
P — PerformanceMeasured by considering processing speed, response time, resource consumption, throughput, and efficiency.
S — SupportabilityCombines the ability to extend the program (extensibility), adaptability, and serviceability.
FURPS is a frequently tested acronym. Make sure you can expand it and explain each attribute with an example.

Software Design Concepts

The software design concept describes the idea or principle behind the design. It describes how you plan to solve the problem of designing software — the logic or thinking behind how you will design software. It allows the software engineer to create the model of the system to be developed.

The fundamental design concepts are:

  • Abstraction — data, procedure, control
  • Architecture — the overall structure of the software
  • Patterns — "conveys the essence" of a proven design solution
  • Separation of concerns — any complex problem can be more easily handled if it is subdivided into pieces
  • Modularity — compartmentalization of data and function
  • Hiding — controlled interfaces
  • Functional independence — single-minded function and low coupling
  • Refinement — elaboration of detail for all abstractions
  • Aspects — a mechanism for understanding how global requirements affect design
  • Refactoring — a reorganization technique that simplifies the design
  • OO design concepts
  • Design Classes — provide design detail that will enable analysis classes to be implemented

1. Abstraction

The process of hiding the complex properties or characteristics from the software itself to keep things more simple.

  • Procedural Abstraction: A sequence of instructions that contain a specific and limited function. The word "open" on a door — the user only knows the concept, but the implementation details (algorithms for mechanisms like pull, push, slide, etc.) are hidden.
  • Data Abstraction: A collection of data that describes a data object. For example, "door" implies a set of attributes: manufacturer, model number, type, swing direction, inserts, lights, locking mechanism, weight, opening mechanism — all described at a high level, but implemented as a data structure.

2. Architecture

The complete structure of the software is known as software architecture. Structure provides conceptual integrity for a system in a number of ways:

  • Structural Properties: Defines the components of a system (e.g., modules, objects, filters) and the manner in which those components are packaged and interact with one another. For example, objects are packaged to encapsulate both data and the processing that manipulates the data and interact via the invocation of methods.
  • Extra-functional Properties: The architectural design should address how the design architecture achieves requirements for performance, capacity, reliability, security, adaptability, and other system characteristics.
  • Families of Related Systems: The architectural design should draw upon repeatable patterns commonly encountered in the design of families of similar systems. The design should have the ability to reuse architectural building blocks.

3. Patterns

"A pattern is a named nugget of insight which conveys the essence of a proven solution to a recurring problem within a certain context amidst competing concerns."

A design pattern can be characterized as "a three-part rule which expresses a relation between a certain context, a problem, and a solution."

  • Component Pattern: Addresses a specific element of the design such as an aggregation of components to solve some design problem, relationships among elements.
  • Design Pattern: A medium-level pattern type that is used by developers to solve the problem in the design stage of development.

Design Pattern Template

ElementDescription
Pattern NameDescribes the essence of the pattern in a short but expressive name.
IntentDescribes the pattern and what it does.
Also-Known-AsLists any synonyms for the pattern.
MotivationProvides an example of the problem.
ApplicabilityNotes specific design situations in which the pattern is applicable.
StructureDescribes the classes that are required to implement the pattern.
ParticipantsDescribes the responsibilities of the classes required to implement the pattern.
CollaborationsDescribes how the participants collaborate to carry out their responsibilities.
ConsequencesDescribes the "design forces" that affect the pattern and potential trade-offs.
Related PatternsCross-references related design patterns.

4. Modularity

Software is separately divided into named and addressable components. Sometimes they are called modules which integrate to satisfy the problem requirements.

Modularity is the single attribute of a software that permits a program to be managed easily. Monolithic software (i.e., a large program composed of a single module) cannot be easily grasped.

Modularity and Software Cost: There is an optimal number of modules. Too few modules → each module is too complex. Too many modules → integration cost increases due to interfaces. The total cost has a minimum at some intermediate number of modules.

Separation of Concerns

Any complex problem can be more easily handled if it is subdivided into pieces that can each be solved and/or optimized independently. This is a key design principle that modularity supports.

5. Information Hiding

Modules must be specified and designed so that the information like algorithms and data presented in a module is not accessible for other modules not requiring that information.

A module has a controlled interface — a "secret" that it hides. The hidden "secrets" include:

  • Algorithm details
  • Data structure internals
  • Details of external interface
  • Resource allocation policy

Clients interact with the module through the controlled interface only, without knowledge of the internal design decisions.

6. Functional Independence

Functional independence is achieved by developing modules with "single-minded" function and an "aversion" to excessive interaction with other modules. It is assessed using two qualitative criteria:

CriteriaDescription
CohesionAn indication of the relative functional strength of a module. A module should do one thing well (high cohesion is desirable).
CouplingAn indication of the relative interdependence among modules. Modules should have minimal dependencies on each other (low coupling is desirable).
Remember: Good design = High Cohesion + Low Coupling. This is one of the most fundamental design principles in software engineering.

7. Refinement

Stepwise Refinement is the process of breaking down a programming problem into a series of steps. It is a top-down design approach.

  1. You start with a general set of steps to solve the problem, defining each in turn.
  2. Once you have defined each of the steps, you break the problem down into a series of smaller sub-steps.
  3. You keep on going until you have described the problem in such a level of detail that you can code a solution.

Example from slides: Making tea — Step-01: boil water → Step-02: add tea bag → etc. Each step can be further refined into sub-steps.

8. Refactoring

Refactoring is a reorganization technique that simplifies the design (or internal code structure) of a component without changing its function or external behaviour.

It removes:

  • Redundancy
  • Unused design elements
  • Inefficient or unnecessary algorithms
  • Poorly constructed or inappropriate data structures
  • Any other design failures

Design Classes

The requirements model defines a set of analysis classes. There are five different types of design classes, each representing a different layer of the design architecture:

Class TypeDescription
User Interface ClassesDefine all abstractions necessary for human-computer interaction.
Business Domain ClassesRepresent entities from the problem domain (e.g., Customer, Order).
Process ClassesImplement business logic and rules.
Persistent ClassesJava classes whose objects have to be stored in the database tables. They show data stores that will persist beyond the execution of the software.
System ClassesImplement software management and control functions that allow the system to operate and communicate in the computing environment. Belongs to java.lang package (e.g., java.lang.System).

Four Characteristics of a Well-Formed Design Class

  • Complete and Sufficient: A design class should be the complete encapsulation of all attributes and methods that can reasonably be expected to exist for the class. Example: the class Scene for video-editing software is complete only if it contains all attributes and methods that can reasonably be associated with the creation of a video scene. Sufficiency ensures the design class contains only those methods that are sufficient to achieve the intent of the class — no more and no less.
  • Primitiveness: Methods associated with a design class should be focused on accomplishing one service for the class. Once the service has been implemented with a method, the class should not provide another way to accomplish the same thing.
  • High Cohesion: A cohesive design class has a small and focused set of responsibilities. Single-mindedly applied methods and attributes.
  • Low Coupling: All design classes should collaborate with each other, but the minimum acceptable level of collaboration must be kept. If a design model is highly coupled, the system is difficult to implement, test, and maintain over time. This is called the Law of Demeter — a method should only send messages to methods in neighboring classes.
The Law of Demeter ("Don't talk to strangers") is a favorite exam concept. A method should only call methods on: (1) itself, (2) its parameters, (3) objects it creates, (4) its direct component objects.

2. Architectural Design

Architecture vs Design

There is a distinct difference between architecture and design:

  • A design is an instance of an architecture, similar to an object being an instance of a class.
  • Example: Consider the client-server architecture. You can design a network-centric software system in many different ways — using Java EE or .NET. So there is one architecture, but many designs based on it.
  • Software architecture is responsible for the skeleton and high-level infrastructure (the abstract view of the idea).
  • Software design is responsible for the code-level specifics — what each module does, class scope, function purposes (the implementation view of the idea).

What is Architectural Design?

Architectural design is concerned with understanding how a software system should be organized and designing the overall structure of that system. The information is obtained from the requirement model and other information collected during requirement engineering.

Agility and Architecture

It is generally accepted that an early stage of agile processes is to design an overall systems architecture. Refactoring the system architecture is usually expensive because it affects so many components in the system.

Architecture Level of Abstraction

  • Architecture in the Small: Concerned with the architecture of individual programs. How an individual program is decomposed into components.
  • Architecture in the Large: Concerned with the architecture of complex enterprise systems that include other systems, programs, and program components. These may be distributed over different computers, owned and managed by different companies.

Advantages of Explicit Architecture

Non-functional requirements have the most significant effect on the system's architecture ("architecturally significant requirements"). Bass et al. suggest three advantages of explicitly designing and documenting software architecture:

  • Stakeholder communication — architecture is a high-level presentation of the system.
  • System analysis — enables analysis of whether the system can meet non-functional requirements.
  • Large-scale reuse — architecture may be reusable across systems with similar requirements.

Architectural Representations (Block Diagrams)

  • Block diagrams present a high-level picture of the system structure.
  • Each box represents a component.
  • Boxes within boxes indicate a component has been decomposed into subcomponents.
  • Arrows mean data and/or control signals are passed from component to component in the direction of the arrows.

Architectural Design Decisions

Architectural design is a creative process — the process differs depending on the type of system. However, common decisions span all design processes and affect the non-functional characteristics of the system.

Architecture and System Characteristics (Quality Attributes): The architecture directly influences Performance, Security, Safety, Availability, and Maintainability of the system.

Krutchen's 4+1 Architectural Views

It is impossible to represent all relevant information about a system's architecture in a single diagram, as a graphical model can only show one view or perspective. For both design and documentation, you usually need to present multiple views.

1. Logical View

  • Focuses on functional requirements.
  • Shows key abstractions in the system as objects.
  • Describes how the system is structured in terms of units of implementation.
  • Elements: packages, classes, and interfaces.
  • Relationships: dependencies, interface realizations, part-whole relationships.
  • Viewer: End User.
  • Diagrams used: Class Diagram, Sequence Diagram, Communication Diagram.

2. Process View

  • Shows how the system runs at runtime.
  • Focuses on achieving non-functional requirements.
  • Shows how the system is composed of interacting processes.
  • Useful for making judgments about performance and availability.
  • Viewer: Integrators.

3. Development View

  • Shows the decomposition of the system into modules implemented by different development teams.
  • Represents the logical organization of the code.

4. Implementation / Physical View

  • Depicts how the software is deployed in data centers.
  • Example: Web-based app would show which web service is used, number of servers and their roles, software components installed on them.
  • Viewer: System Engineers.
The 4+1 model is a favorite exam topic. Know which viewer (End User, Integrator, System Engineer) maps to which view, and what diagrams are used.

Design Patterns (Overview)

Design patterns solve reoccurring problems in software design. They are categorized into three types:

Creational Patterns

Focus on how to instantiate an object or group of related objects.

  • Abstract Factory, Builder, Factory Method, Prototype, Singleton Pattern

Structural Patterns

Identifying a simple way to realize relationships among entities.

  • Adapter, Bridge, Decorator, Facade, Proxy Pattern

Behavioral Patterns

Identify common communication patterns between objects.

  • Command, Interpreter, Iterator, Mediator, Null Object, Observer

Architectural Patterns

Patterns are a means of representing, sharing and reusing knowledge. An architectural pattern is a stylized description of a good design practice, tried and tested in different environments. Patterns help you build on the collective experience of skilled software engineers.

Patterns should include information about when they are and when they are not useful. Patterns may be represented using tabular and graphical descriptions.

Architectural patterns address issues such as: Performance, High Availability, Scalability, Security, Maintainability, Testing, Deployment, Technology Stack.

Examples of patterns: MVC, MVP, Layered (N-tier), Master-Slave, REST, Monolithic, Microservice, Event-Driven Architecture (EDA), Service-Oriented Architecture (SOA).

A. Model-View-Controller (MVC) Pattern

The MVC framework is an architectural pattern that separates an application into three main logical components. It is widely used in modern web applications and generally used on applications that run on a single graphical workstation.

ComponentResponsibility
ModelData-related logic. Communicates with the controller. Can sometimes update the view directly or through the controller (depends on framework).
ViewWhat the end user sees. Usually consists of HTML/CSS. Communicates with controller.
ControllerProcesses user requests. Gets data from the user. Acts as intermediary between Model and View.

Demo Example from slides:

  • A DemoModel object has instance variables for storing an array of Points and a color.
  • DemoController implements the MouseMotionListener interface (mouseDragged and mouseMoved) and the ListSelectionListener interface (valueChanged).
  • DemoView is a subclass of JFrame.

Popular MVC Frameworks: ASP.NET MVC, Django, Ruby on Rails, Spring MVC, AngularJS, Laravel.

B. Layered Architecture (N-Tier)

Components are organized in horizontal layers. This is the traditional method for designing most software and is meant to be self-independent — all components are interconnected but do not depend on each other.

Key Point: Layered architecture is the best choice when security is highly concerned.

The Four Standard Layers

LayerDescription
Presentation LayerContains all user interfaces exposed to a user. May provide web, desktop, and native mobile applications.
Business Logic LayerHandles all business logic, validations, and business processes.
Data Access LayerResponsible for interacting with a database. Also known as the persistence layer.
Data Store LayerThe actual data store for the application (database).

Advantages

The advantage of a layered architecture is the separation of concerns — each layer focuses solely on its role. This makes it:

  • Maintainable — changes in one layer don't affect others.
  • Testable — layers can be tested independently.
  • Easy to assign separate "roles" to development teams.
  • Easy to update and enhance layers separately.

Example: A business user requests customer information → the request passes through Presentation → Business Logic → Data Access → Data Store and the response flows back up.

C. Repository / Data Center Architecture

  • Data is stored in a central shared repository.
  • Components interact through the repository only.
  • Components do not interact directly with each other.
  • It is a data-centric architecture that supports user interaction for data processing.

Example: Compiler/IDE (Eclipse) — All data (symbol tables, syntax trees, etc.) in the system is managed in a central repository accessible to all system components (editor, compiler, debugger, etc.).

D. Client-Server Architecture

A computing model in which the server hosts, delivers and manages most of the resources and services to be consumed by the client. One or more client computers are connected to a central server over a network or internet connection.

Components

  • Client: Software/application that takes input and sends requests to servers.
  • Server: Software that receives and processes requests from clients.
  • Load Balancer: Distributes incoming network traffic across a group of backend servers to optimize resource usage.

Request Flow (from slides)

  1. Client requests data from server.
  2. Load balancer routes the request to the appropriate server.
  3. Server processes the request.
  4. Server queries appropriate database for data.
  5. Database returns queried data to server.
  6. Server processes the data and sends it back to client.
  7. This process repeats.

Examples: Web Server, Mail Server.

E. Pipe and Filter Architecture

A model of the runtime organization of a system where functional transformations process inputs and produce outputs. Independent entities called filters (components) perform transformations on data, and pipes serve as connectors for the stream of data being transformed.

  • Many systems require transforming streams of discrete data items from input to output.
  • Many types of transformations occur repeatedly → desirable to create them as independent, reusable parts (Filters).
  • The name comes from the original Unix system where processes could be linked using "pipes."
  • Best suited for: Batch processing systems and embedded systems where there is limited user interaction.

Example: Compilers: Lexical Analysis → Parsing → Semantic Analysis → Code Generation. Also: Signal Processing pipelines.

3. Application Architectures

What are Application Architectures?

Application systems are intended to meet a business or organizational need. Businesses have much in common (hiring, invoicing, accounting), which has led to generic software architectures describing the structure and organization of particular types of software systems. The application architecture may be reimplemented when developing new systems.

Uses of Application Architecture Models

  • Starting point for the architectural design process.
  • Design checklist — base your initial design on a generic application architecture if unfamiliar with the type of application.
  • Assessing components for reuse — compare existing components with generic structures.
  • Organizing the work of the development team — identifies stable structural features.
  • Vocabulary for talking about and comparing applications.

Types of Application Architecture

TypeDescriptionExamples
Data ProcessingData-driven apps that process data in batches without explicit user intervention.Scientific data processing, commercial data processing, data analysis.
Transaction ProcessingData-centered apps that process user requests and update a system database.E-commerce, bank transfers.
Event ProcessingSystem actions depend on interpreting events from the environment.Wireless sensor applications.
Language ProcessingUsers' intentions are specified in a formal language that is processed and interpreted by the system.Compilers, Natural Language Processing.

Transaction Processing Systems

Process user requests for information from a database or requests to update the database. Organized so that user actions can't interfere with each other and the integrity of the database is maintained.

From a user perspective, a transaction is: Any coherent sequence of operations that satisfies a goal (e.g., find the times of flights from London to Paris).

Examples: Interactive banking systems, e-commerce systems, information systems, and booking systems. Users make asynchronous requests for service which are then processed by a transaction manager.

ATM System Architecture: The slides show an ATM system architecture as an example of transaction processing, where the ATM communicates with a central banking server through a transaction processing middleware.

Information Systems Architecture

Information systems are almost always web-based systems where the UI is implemented in a web browser. All systems that involve interaction with a shared database can be considered transaction-based information systems.

Examples: Library catalog, flight timetable, records of patients in a hospital.

Information systems have a generic layered architecture:

  • The user interface
  • User communications
  • Information retrieval
  • System database

Web-based Information Systems

In an e-commerce system, the application-specific layer includes additional functionality supporting a 'shopping cart' — users can place items in separate transactions, then pay for them all together in a single transaction.

Server Implementation (Multi-tier)

  • Web server: Responsible for all user communications, with the UI implemented using a web browser.
  • Application server: Responsible for implementing application-specific logic as well as information storage and retrieval requests.
  • Database server: Moves information to and from the database and handles transaction management.

Language Processing Systems

Systems in which the user's intentions are expressed in a formal language (such as a programming language). The system processes this language into an internal format and then interprets this internal representation.

The best known are compilers, which translate high-level language programs into machine code. Also used to interpret command languages for databases and markup languages such as XML.

Compiler Components

  • Lexical Analyzer: Takes input language tokens and converts them to an internal form.
  • Symbol Table: Holds information about names of entities (variables, class names, object names) used in the text being translated.
  • Syntax Analyzer: Checks the syntax of the language being translated.
  • Syntax Tree: An internal structure representing the program being compiled.

4. User Interface Design

Why Care About UI Design?

Interface inconsistency can cost a big company millions of dollars in lost productivity. Software becomes more popular if its user interface is:

  • Attractive
  • Simple to use
  • Responsive in short time
  • Clear to understand
  • Consistent on all interfacing screens

What Does Interface Design Focus On?

  • The design of interfaces between software components.
  • The design of interfaces between the software and other nonhuman producers and consumers of information.
  • The design of the interface between a human and the computer.

GUIs have helped eliminate many horrific interface problems. However, some are still difficult to learn and hard to use. User interface analysis and design has to do with the study of people and how they relate to technology.

The 3 Golden Rules

Golden Rule 1: Place the User in Control

  • Provide for flexible interaction: Different users have different interaction preferences; choices should be provided (keyboard commands, mouse, digitizer pen, multitouch screen, voice recognition).
  • Define interaction modes that don't force unnecessary actions: Example — if spell check is selected in a word-processor, the user should be able to make a small text edit without being forced to remain in spell-checking mode. The user should enter and exit the mode with little or no effort.
  • Allow user interaction to be interruptible and undoable: The user should be able to "undo" any action.
  • Hide technical internals from the casual user: The user should not be aware of OS or file management functions.
  • Design for direct interaction with objects that appear on the screen: The user feels a sense of control when able to manipulate objects in a manner similar to what would occur if the object were a physical thing.

Golden Rule 2: Reduce the User's Memory Load

  • Reduce demand on short-term memory: The interface shall reduce the user's requirement to remember past actions and results by providing visual cues.
  • Establish meaningful defaults: The system shall provide default values that make sense to the average user but allow changes.
  • Define shortcuts that are intuitive: Provide mnemonics (i.e., Ctrl or Alt combinations).
  • Visual layout based on real-world metaphor: The screen layout shall contain well-understood visual cues that the user can relate to real-world actions.
  • Disclose information in a progressive fashion: The interface shall be organized hierarchically, moving the user progressively in a step-wise fashion from an abstract concept to a concrete action (e.g., text format options → format dialog box).

Golden Rule 3: Make the Interface Consistent

  • Allow the user to put the current task into a meaningful context: Provide indicators (e.g., window titles, consistent color coding) that enable the user to know the context of the work at hand.
  • All visual information shall be organized according to a design standard maintained throughout all screen displays.
  • Input mechanisms shall be constrained to a limited set used consistently throughout the application.
  • Mechanisms for navigating from task to task shall be consistently defined and implemented.
  • Maintain consistency across a family of applications: A set of applications performing complementary functionality shall all implement the same design rules.
Golden Rules are highly likely exam questions. Memorize each sub-point with its example (e.g., spell-check mode for Rule 1, Ctrl+combinations for Rule 2).

Four UI Analysis & Design Models

1. User Profile Model

  • Establishes the profile of the end-users of the system.
  • Based on: age, gender, physical abilities, education, cultural/ethnic background, motivation, goals, and personality.
  • Considers syntactic knowledge of the user — the mechanics of interaction required to use the interface effectively.
  • Considers semantic knowledge of the user — the underlying sense of the application; an understanding of the functions performed, meaning of I/O, and objectives of the system.

2. Design Model

  • Derived from the analysis model of the requirements.
  • Incorporates data, architectural, interface, and procedural representations of the software.
  • Constrained by information in the requirements specification that helps define the user of the system.
  • Normally is incidental to other parts of the design model, but in many cases it is as important as the other parts.

3. Implementation Model

  • Consists of the look and feel of the interface combined with all supporting information (books, videos, help files) that describe system syntax and semantics.
  • Strives to agree with the user's mental model; users then feel comfortable with the software and use it effectively.
  • Serves as a translation of the design model by providing a realization of the information contained in the user profile model and the user's mental model.

4. User's Mental Model

  • Often called the user's system perception.
  • Consists of the image of the system that users carry in their heads.
  • Accuracy of the description depends upon the user's profile and overall familiarity with the software in the application domain.
Key Principle: An effective design is one in which the User's Mental Model and the Implementation Model coincide.

UI Design Process (Spiral Model)

The analysis and design process for user interfaces is iterative and can be represented using a spiral model. Since it's a spiral model, these steps need to be processed again and again:

  1. Interface Analysis and Modeling
  2. Interface Design
  3. Interface Construction: Create prototypes against use-case scenarios & validate the design.
  4. Interface Validation: Focuses on — Does the system accommodate all variety of tasks? Is the system easy to use & learn? Is there user acceptance of the system as a useful tool?

Interface Analysis

Understand the problem before designing the solution. Understand:

  1. The people (end users) who will interact with the system.
  2. The tasks that end users must perform.
  3. The content that is presented as part of the interface.
  4. The environment in which these tasks will be conducted.

User Analysis

Information for system understanding can be obtained by:

  • User Interviews: Software team members meet with end users to identify their needs and work culture (one-on-one meetings or focus groups).
  • Sales Input: Sales people meet with users to assess user categories & understand requirements.
  • Marketing Input: Market surveys checking how many ways the product could be useful.
  • Support Input: Support staff takes feedback on what works/what doesn't, which features are easy to use or not.

User Analysis Questions for Better User Categorization

  • Are users trained professionals, technicians, clerical, or manufacturing workers?
  • What level of formal education does the average user have?
  • Are users capable of learning from written materials or do they desire classroom training?
  • Are users expert typists or keyboard-phobic?
  • What is the age range of the user community?
  • What is the user's gender distribution?
  • Do users work normal office hours or until the job is done?
  • Is the software integral to their work or used occasionally?
  • What is the primary spoken language among users?
  • What are the consequences if a user makes a mistake?
  • Are users experts in the subject matter? Do they want to know about the underlying technology?

Task Analysis & Modelling

Goal is to answer: What work will the user perform? What tasks/subtasks will be performed? What objects will the user manipulate? What is the sequence of work tasks (workflow)? What is the hierarchy of tasks?

Techniques applied to the UI:

  • Use Cases: Define basic interaction of actor and system, written using informal paragraphs. Can be used to derive tasks, subtasks, and interfaces.
  • Task Elaboration: Stepwise elaboration or task refinement of interactive tasks (functional decomposition). Example: "furniture layout" can be refined into subtasks like (1) draw floor plan, (2) place windows/doors, (3a) use furniture templates, (3b) use accent templates, (4) move outlines for best placement, (5) label outlines, (6) draw dimensions, (7) draw perspective-rendering view.
  • Object Elaboration: Extract physical objects from system to define their classes and behavior. Example: "furniture template" translates into a class called Furniture with attributes like size, shape, location.
  • Workflow Analysis: Defines how a work process is completed when several people and roles are involved. Shown using UML Swimlane diagrams. Example: Different users (patient, pharmacist, physician) implement different tasks, so look and feel of each interface differs. The interface for pharmacists and physicians must accommodate secondary information sources (e.g., inventory, alternative medications).

Hierarchical Task Representation Example

User task: Requests that a prescription be refilled → Subtasks: Provide identifying information → Specify name → Specify userid → Specify PIN and password → Specify prescription number → Specify date refill is required.

Analysis of Display Content

  • Format of the content, aesthetics.
  • Content displayed using stepwise refinement approach.

Analysis of the Work Environment

  • Work environment should be helpful in proper operation and concentration.
  • Must co-relate with the designed software aesthetics.
  • People are influenced by activity around them — lighting, noise, display height, keyboard access.
  • Will system interaction be measured (time per transaction, accuracy)?
  • Will two or more people share information before an input can be provided?
  • How will support be provided to users?

Interface Design Steps

  1. Define interface objects and actions (operations) using information developed during interface analysis.
  2. Define events (user actions) that will cause the state of the user interface to change.
  3. Model this behavior.
  4. Depict each interface state as it will actually look to the end-user.
  5. Indicate how the user interprets the state of the system from information provided through the interface.

Applying Interface Design Steps

Once objects and actions have been defined and elaborated iteratively, they are categorized by type:

  • Source object: e.g., a report icon — dragged and dropped onto a target.
  • Target object: e.g., a printer icon.
  • Application object: Represents application-specific data. e.g., a mailing list that can be sorted, merged, or purged (menu-based actions) but is not dragged and dropped via user interaction.

Interface Construction & Implementation (WebApp)

  1. Review information from the requirements model and refine as required.
  2. Develop a rough sketch of the WebApp interface layout.
  3. Map user objectives into specific interface actions.
  4. Define user tasks associated with each action.
  5. Storyboard screen images for each interface action.
  6. Refine interface layout and storyboards using aesthetic design input.
  7. Identify user interface objects required to implement the interface.
  8. Describe the interface layout for each state.
  9. Refine and review the interface design model.

Design Issues

Issue 1: System Response Time

Primary complaint for almost every interactive system. Two characteristics:

  • Length: Longer response times are not appreciated and lead to user frustration. If response is too long → inform user about delay.
  • Variability: Varying response time leads to user confusion — the user wonders whether something went wrong at the backend, leading to a different response time than the average.

Issue 2: Help Facilities

  • Online helpdesk, detailed user manuals.
  • Help availability for all functionalities?
  • How will the user demand help? (Menu or function key mapped to help)
  • How is help presented? (via another window or a printed manual)
  • How to return to normal UI after consulting help?

Issue 3: Error Handling

Error messages & warnings are bad news. Error messages must be explanatory and should include some remedies. A good error message includes:

  • Describe the problem in plain language the user can understand.
  • Provide constructive advice for recovering from the error.
  • List the negative consequences of the error (e.g., potentially corrupted data files).
  • Be accompanied by an audible or visual cue (beep, momentary flash, error color).
  • Be non-judgmental — never place blame on the user.

Issue 4: Menu & Command Labeling

Different styles: command-oriented architecture and UI-based architecture. How commands are assigned to each menu item so that it may run without UI as well.

Issue 5: Application Accessibility

UI should cater to the needs of physically challenged persons (e.g., voice inputs to facilitate handicapped users).

Issue 6: Internationalization

UI must target the global market. Follow global design standards & facilitate multiple languages.

Interface Design Principles for WebApps

Anticipation

A WebApp should be designed so that it anticipates the user's next move. Example: If a user requests info about a printer driver for a newly released OS, the designer should anticipate that the user might want to download the driver and provide navigation facilities for this.

Communication

The interface should communicate the status of any activity initiated by the user (e.g., paper moving through a printer icon).

Consistency

The use of navigation controls, menus, icons, and aesthetics (color, shape, layout) should be consistent throughout the WebApp.

Controlled Autonomy

The interface should facilitate user movement throughout the WebApp — an environment that is neither confining nor infinite (Golden Rule: place user in control). E.g., navigation to a secure portion should be restricted by userid and password.

Efficiency

The design should optimize the user's work efficiency, not the efficiency of the web engineer. Example: Requiring customers to enter telephone numbers without spacing or punctuation saves a single line of code but makes the user's life harder — don't do this.

Focus

The WebApp interface should stay focused on the user task(s) at hand.

Latency Reduction

Rather than making the user wait for some internal operation to complete (e.g., downloading a complex graphical image), the WebApp should use multitasking.

Learnability

A WebApp interface should be designed to minimize learning time, and once learned, to minimize relearning required when the WebApp is revisited.

Fitt's Law

Fitt's Law states that the time to acquire a target is a function of the distance to and size of the target. This means:

  • Design large targets (big buttons) for important functions — they're easier to interact with.
  • Better to support immediate selection of interactive elements than dropdown menus, as the user doesn't have to move the cursor from its current position.
  • The time required to acquire multiple targets is the sum of the time to acquire each. So reduce distances, increase target sizes, and reduce the total number of targets to increase efficiency.
Fitt's Law is a frequently tested concept. Remember: bigger buttons = faster interaction, and total interaction time = sum of all individual target acquisitions.

5. Software Testing

What is Software Testing?

Software testing is an investigation conducted to provide stakeholders with information about the quality of the product or service under test. When you test software, you execute a program using artificial data. You check the results for errors, anomalies, or information about non-functional attributes.

Program testing can show the presence of bugs, but never their absence.

Testing Process Goals

GoalDescriptionSuccess Criteria
Validation TestingDemonstrate to developer and customer that software meets its requirements.A successful test shows the system operates as intended.
Defect TestingDiscover faults or defects where behavior is incorrect or doesn't conform to spec.A successful test makes the system perform incorrectly and exposes a defect.

Defect Testing sub-categories: Data Corruption, Wrong Computation, Unwanted Interaction, System Crashes.

Verification vs Validation

VerificationValidation
Question"Are we building the product right?""Are we building the right product?"
FocusSoftware should conform to its specification.Software should do what the user really requires.

Example from slides: A clickable button with name "Submet" — Verification would check the design doc and correct the spelling mistake to "Submit." Once the code is ready, Validation is done to check if the button performs its intended function.

V & V Confidence

The goal of V&V processes is to establish confidence that the software system is "fit for purpose." Level of confidence depends on:

  • Software Purpose: The more critical the software, the more important reliability is.
  • Marketing Environment: A company may release a program before fully tested to be first to market.
  • User Expectations: Users may have low initial expectations for certain types of software.

Software Inspections vs Testing

Inspections (Static V&V)Testing (Dynamic V&V)
Analysis of the static system representation to discover problems.Exercising and observing product behaviour.
May be supplemented by tool-based document and code analysis.The system is executed with test data and its operational behaviour is observed.
Focus on source code, requirements, design models — any readable representation.Requires the system to actually run.

What Can Be Inspected?

Requirements specification, System prototype, Software architecture, UML design models, Database schemas, Program code.

Advantages of Inspections

  • During testing, errors can mask (hide) other errors. Inspection is static — no concern with interactions between errors.
  • Incomplete versions of a system can be inspected without additional costs. If a program is incomplete, you need specialized test harnesses.
  • Inspections can also consider broader quality attributes: compliance with standards, portability, maintainability, inefficiencies, inappropriate algorithms, and poor programming style.

Stages of Testing

There are three stages: Development Testing → Release Testing → User Testing

Development Testing

Includes all testing activities carried out by the team developing the system. It is primarily a defect testing process, interleaved with debugging (locating problems and fixing them).

  • Unit Testing: Individual program units or object classes are tested.
  • Component Testing: Several individual units are integrated to create composite components.
  • System Testing: Some or all components in a system are integrated and tested as a whole.

Unit Testing

The process of testing individual program components in isolation — such as methods or object classes. Individual functions or methods are the simplest type of component. Your tests should be calls to these routines with different input parameters.

Object Class Testing

Complete test coverage of a class involves:

  • Testing all operations associated with an object.
  • Setting and interrogating all object attributes.
  • Exercising the object in all possible states.
  • Inheritance makes it more difficult to design object class tests as information to be tested is not localised.

Weather Station Example (from slides):

Need to define test cases for reportWeather, startup, and shutdown. Using a state model, identify sequences of state transitions:

  • Shutdown → Running → Shutdown
  • Configuring → Running → Testing → Transmitting → Running
  • Running → Collecting → Running → Summarizing → Transmitting → Running

Automated Test Components

  • Setup part: Initialize the system with the test case (inputs and expected outputs).
  • Call part: Call the object or method to be tested.
  • Assertion part: Compare the result of the call with the expected result. If assertion evaluates to true → test successful; if false → test failed.

Choosing Unit Test Cases

Test cases should show that:

  1. When used as expected, the component does what it is supposed to do (normal operation).
  2. Based on testing experience, use abnormal inputs to check they are properly processed and don't crash the component.

Two strategies for choosing test cases:

  • Partition Testing (Equivalence Partitioning)
  • Guideline-Based Testing

Equivalence Partitioning

Input data and output results often fall into different classes where all members of a class are related. Each class is an equivalence partition or domain where the program behaves in an equivalent way for each class member.

Test cases should be chosen from each partition.

How it works: Identify groups of inputs that have common characteristics and should be processed the same way. Choose tests from within each group. Include both valid and invalid partitions.

Testing Guidelines (Sequences)

  • Test software with sequences having a single value.
  • Use sequences of different sizes in different tests.
  • Tests to access the first, middle, and last elements.
  • Test with sequences of zero length.

General Testing Guidelines

  • Repeat the same input numerous times.
  • Choose inputs that force the system to generate all error messages.
  • Design inputs that cause input buffers to overflow.
  • Force invalid outputs to be generated.
  • Force computation results to be too large or too small.

Component Testing

A sub-category of software testing in which each individual component is separately tested without integrating with other components. Also known as module testing, when viewed from an architecture perspective.

  • Software components are composite components of several interacting objects.
  • Access functionality through defined component interfaces.
  • Focus on showing that the component interface behaves according to its specification.

Interface Testing

Objectives are to detect faults due to interface errors or invalid assumptions about interfaces. Interface testing is done during integration of components for system testing.

Types of Interfaces

TypeDescription
Parameter InterfacesData passed from one method or procedure to another.
Shared Memory InterfacesBlock of memory shared between procedures or functions.
Procedural InterfacesEncapsulates set of procedures called by other sub-systems.
Message Passing InterfacesSub-systems request services from other sub-systems.

System Testing

Involves integrating components to create a version of the system and then testing the integrated system. Focus is on testing the interactions between components.

  • Checks that components are compatible, interact correctly, and transfer the right data at the right time across their interfaces.
  • Tests the emergent behaviour of a system.
  • Reusable and off-the-shelf components may be integrated with newly developed components.
  • System testing is a collective rather than an individual process.
  • In some companies, a separate testing team with no involvement from designers and programmers may do system testing.

Test-Driven Development (TDD)

An approach to program development in which you inter-leave testing and code development. Tests are written before code and 'passing' the tests is the critical driver. Introduced as part of agile methods such as Extreme Programming, but can also be used in plan-driven processes.

The Fundamental TDD Process

  1. Identify the increment of functionality that is required.
  2. Write a test for this functionality and implement it as an automated test.
  3. Run the test — it should FAIL (because functionality isn't implemented yet).
  4. Implement the functionality and re-run the test. This may involve refactoring existing code.
  5. Once all tests run successfully, move on to the next chunk of functionality.

TDD Cycle

Add Test → Watch Test Fail → Write Code → Run Tests → Refactor → (repeat)

Benefits of TDD

  • Code coverage: Every code segment you write has at least one associated test.
  • Regression testing: A test suite is developed incrementally. You can always run regression tests to check that changes haven't introduced new bugs.
  • System documentation: Tests themselves act as documentation describing what the code should do.
  • Simplified debugging: When a test fails, it should be obvious where the problem lies.

Regression Testing

Involves running test sets that have successfully executed after changes have been made. Checks that changes have not introduced new bugs and that new code interacts as expected with existing code. Regression testing is expensive and sometimes impractical when a system is manually tested.

Release Testing

The process of testing a particular release intended for use outside the development team. The primary goal is to convince the supplier that the system is good enough for use.

Release testing has to show that the system delivers its specified functionality, performance and dependability, and that it does not fail during normal use.

Release testing is usually a black-box testing process where tests are only derived from the system specification.

Release Testing vs System Testing

  • A separate team (not involved in development) should be responsible for release testing.
  • System testing by the development team focuses on discovering bugs (defect testing).
  • Release testing objective: Check that the system meets requirements and is good enough for external use (validation testing).

Performance Testing

Part of release testing. A software application's performance — response time, reliability, resource usage, and scalability — matters. The goal is not to find bugs but to eliminate performance bottlenecks.

Types of Performance Testing

TypeDescription
Load TestingChecks the application's ability to perform under anticipated user loads. Objective: identify bottlenecks before going live.
Stress TestingTests under extreme workloads to see how it handles high traffic or data processing. Objective: identify the breaking point.

Example Performance Test Cases (from slides)

  • Verify response time is not more than 4 seconds when 1000 users access the website simultaneously.
  • Verify response time under load is within acceptable range when network connectivity is slow.
  • Check maximum number of users the application can handle before it crashes.
  • Check database execution time when 500 records are read/written simultaneously.
  • Check CPU and memory usage under peak load.
  • Verify response time under low, normal, moderate, and heavy load conditions.

Real-World Load Testing Failures (from slides)

  • Target.com lost $780,000 in sales in just 3 hours when the site was down during a promotion in 2015.
  • Amazon.com servers crashed in 2013 for 30 minutes — lost $66,240 per minute.
  • Virgin Blue airlines experienced outages for 11 days, leading to a loss of $20 million.

Load Testing Tools: LoadNinja, Eggplant, LoadRunner.

Stress Testing Details

Includes testing the behavior of software under abnormal conditions. The aim is to identify the breaking point. It tests the failure behaviour of the system. Scenarios include:

  • Shutdown or restart of network ports randomly.
  • Turning the database on or off.
  • Running different processes that consume resources such as CPU, memory, server.

User Testing

A stage where users or customers provide input and advice on system testing. User testing is essential even when comprehensive system and release testing have been carried out, because influences from the user's working environment (reliability, performance, usability, robustness) cannot be replicated in a testing environment.

Types of User Testing

TypeDescription
Alpha TestingUsers work with the development team to test software at the developer's site.
Beta TestingA release is made available to users to allow them to experiment and raise problems they discover.
Acceptance TestingCustomers test a system to decide whether to accept it from developers and deploy it. Primarily for custom systems.

Stages in the Acceptance Testing Process

  1. Define acceptance criteria.
  2. Plan acceptance testing.
  3. Derive acceptance tests.
  4. Run acceptance tests.
  5. Negotiate test results.
  6. Reject/accept system.

Basis Path Testing

The objective of path testing is to ensure that the set of test cases is such that each path through the program is executed at least once.

The starting point is a program flow graph that shows nodes representing program decisions and arcs representing the flow of control.

Steps for Basis Path Testing

  1. Draw a control flow graph to determine different program paths.
  2. Calculate Cyclomatic Complexity — a metric to determine the number of independent paths. Formula: V = E − N + 2 (E = number of edges, N = number of nodes).
  3. Find a basis set of independent paths.
  4. Generate test cases to exercise each path.

Detailed Example (Shipping Calculator from Slides)

public double calculate(int amount) {
  -1-  double rushCharge = 0;
  -1-  if (nextday.equals("yes")) {
  -2-    rushCharge = 14.50;
       }
  -3-  double tax = amount * .0725;
  -3-  if (amount >= 1000) {
  -4-    shipcharge = amount * .06 + rushCharge;
       }
  -5-  else if (amount >= 200) {
  -6-    shipcharge = amount * .08 + rushCharge;
       }
  -7-  else if (amount >= 100) {
  -8-    shipcharge = 13.25 + rushCharge;
       }
  -9-  else if (amount >= 50) {
  -10-   shipcharge = 9.95 + rushCharge;
       }
  -11- else if (amount >= 25) {
  -12-   shipcharge = 7.25 + rushCharge;
       }
       else {
  -13-   shipcharge = 5.25 + rushCharge;
       }
  -14- total = amount + tax + shipcharge;
  -14- return total;
}

Step 1: Draw the flow graph from labeled nodes 1–14.

Step 2: Calculate Cyclomatic Complexity: V = E − N + 2 = 19 − 14 + 2 = 7

Step 3: Determine the 7 independent paths:

  • P-01: 1, 2, 3, 5, 7, 9, 11, 13, 14
  • P-02: 1, 3, 4, 14
  • P-03: 1, 3, 5, 6, 14
  • P-04: 1, 3, 5, 7, 8, 14
  • P-05: 1, 3, 5, 7, 9, 10, 14
  • P-06: 1, 3, 5, 7, 9, 11, 12, 14
  • P-07: 1, 3, 5, 7, 9, 11, 13, 14

Step 4: Generate test cases for each path with specific values for amount and nextday to exercise each unique path.

Binary Search Flow Graph Example

Paths:

  • Path 1: 1, 2, 3, 5, 6, 7
  • Path 2: 1, 2, 4, 5, 6, 7
  • Path 3: 1, 6, 7

Advantages of Basic Path Testing

  • Helps reduce redundant tests.
  • Focuses attention on program logic.
  • Helps facilitate analytical versus arbitrary case design.
  • Test cases which exercise basis set will execute every statement in a program at least once.
Basis Path Testing is a highly likely scenario question. Practice: (1) drawing flow graphs from code, (2) calculating V = E − N + 2, (3) listing independent paths, and (4) writing test case values for each path.

Architecture Pattern
Scenario 1: A national bank needs a new internal fund-processing module. The system requires ultra-strict security constraints where database interactions must be completely isolated from the user presentation layer. Layered Architecture (N-Tier Pattern) is the best choice.

MVC Pattern

Verification vs Validation

Pipe & Filter
Scenario 14: A signal processing system receives raw audio data and transforms it through: Noise Reduction → Frequency Analysis → Compression → Encoding → Output. Each step is independent and reusable. Which architectural pattern is this, and why is it suited for this type of system?

Pipe and Filter Architecture.

Each processing step (Noise Reduction, Frequency Analysis, etc.) is an independent filter that transforms data and passes it via pipes to the next filter. The slides state this pattern is "best suited to batch processing systems and embedded systems where there is limited user interaction" and uses Signal Processing as a direct example. Each transformation occurs repeatedly in practice, so it's desirable to create them as independent, reusable parts — exactly what this system does.

Component Testing
Scenario 15: Two development teams built Module A and Module B independently. When integrated, Module A sends data in XML format but Module B expects JSON. What type of testing would catch this, and what is the specific type of interface involved?

Interface Testing (part of Component Testing) would catch this. The objective of interface testing is to detect faults due to interface errors or invalid assumptions about interfaces.

The interface type involved is a Message Passing Interface — where sub-systems request services from other sub-systems. The data format mismatch (XML vs JSON) represents an invalid assumption about the interface contract.
